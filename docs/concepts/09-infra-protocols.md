# 파트 9. 인프라 프로토콜 & 서비스 보안

애플리케이션 계층의 핵심 프로토콜(DNS/HTTP/FTP/SNMP/DHCP) 동작 원리와, 이메일·데이터베이스·클라우드 서비스의 보안을 다룹니다. 기존 [네트워크 보안](01-network.md)·[웹 보안](02-web.md) 파트와 함께 애플리케이션 계층 전반을 이룹니다.

## 1. DNS 동작 방식 심화

### 1-1. 네임서버 종류와 질의 방식

| 용어 | 설명 |
|---|---|
| Recursive(Cache) 네임서버 | "재귀적"이라는 뜻으로, 동일한 작업을 조건이 만족될 때까지 반복적으로 처리한다는 의미. 관리하는/위임받은 도메인 없이 사용자 호스트로부터 질의가 들어오면 자신의 캐시에 저장된 정보 또는 반복적 질의(Iterative Query)를 통해 그 결과를 사용자 호스트에 응답. 일반적으로 ISP가 제공하는 DNS 서버가 해당 |
| Authoritative 네임서버 | "권한 있는"이라는 뜻으로, 관리하는/위임받은 도메인을 가지고 있는 네임서버. 특정 도메인에 대한 정보를 관리하면서 해당 도메인에 대한 질의에만 응답. 네임서버가 관리하는 도메인 영역을 존(Zone)이라 하고, 관리 도메인에 대한 정보를 담고 있는 파일을 '존 파일(Zone File)'이라 함 |
| 재귀적 질의 (Recursive Query) | 사용자 호스트가 Recursive 네임서버로 질의할 때 사용되는 방식. 캐시에 데이터가 있으면 즉시 반환하고, 없으면 최상위 Root 네임서버부터 대상 도메인 네임서버까지 반복적 질의를 수행한 후 결과를 반환 |
| 반복적 질의 (Iterative Query) | Recursive 네임서버가 도메인을 관리하는 각 Authoritative 네임서버로 질의할 때 사용하는 방식. 최상위 Root부터 계층구조에 따라 위임된 네임서버 정보에 따라 순차적으로 반복 진행 |

### 1-2. 질의 순서 및 실무 팁

1. 사용자 호스트가 도메인/URL 접속 시 **로컬 DNS 캐시** 검색
2. 캐시에 없으면 **hosts 파일** 검색 (Windows: `%SystemRoot%\System32\drivers\etc\hosts`)
3. 그래도 없으면 시스템에 설정된 **DNS 서버**로 질의(Recursive Query)

!!! tip "hosts.ics 파일 (실무 함정)"
    윈도우에서 인터넷 연결 공유(ICS: Internet Connection Sharing) 기능 사용 시 클라이언트의 IP를 강제로 지정하는 `hosts.ics` 설정 파일이 생성될 수 있다. hosts.ics는 일반 hosts 파일보다 DNS 질의 검색 우선순위가 높아 먼저 참조되는 특성이 있으므로, 악성코드에 의해 조작된 hosts.ics 파일로 파밍 사이트 접속을 유도하는 보안 사고 사례가 있어 주의해야 한다.

**DNS 캐시 확인 명령어(Windows)**: `ipconfig /displaydns`

## 2. HTTP 프로토콜 심화

### 2-1. 개요

- 웹(Web)상에서 클라이언트와 서버 간 통신을 위해 개발된 프로토콜. 웹(WWW: World Wide Web)은 전 세계에 거미줄처럼 연결된 망이라는 의미
- 주로 80/tcp 포트 사용. 1991년 HTTP 0.9(초기 버전) 발표 이후 1996년 1.0, 1999년 1.1 버전이 발표되어 널리 사용
- HTTP 통신은 클라이언트 요청(Request)과 서버 응답(Response)으로 이루어짐

### 2-2. 비연결형(Connectionless) 프로토콜과 Keep-Alive

| 방식 | 동작 |
|---|---|
| Connection: close (HTTP/1.0까지) | 클라이언트의 HTTP 요청에 대한 서버의 응답 이후 **TCP 연결을 바로 종료**하는 구조. 제한된 서버 연결 자원으로 최대한 많은 클라이언트 요청을 처리하기 위함이나, 서버 입장에서는 다수의 TCP 연결 설정·종료에 대한 부하가 발생 |
| Connection: Keep-Alive (HTTP/1.1부터) | 응답 헤더에 Keep-Alive 옵션이 추가되어, 웹서버 설정에 따라 **일정 시간 TCP 연결 상태를 지속**시켜 한 번의 연결로 여러 요청/응답을 반복할 수 있음. `timeout`(연결 지속 시간)과 `max`(연결을 지속하는 동안 허용할 최대 요청 건수) 옵션으로 제어 (아파치 설정파일 `httpd.conf`에서 설정) |

## 3. FTP 프로토콜 심화

### 3-1. 개요와 보안 대안

- FTP(File Transfer Protocol)는 TCP/IP 기반의 서버-클라이언트 간 파일 전송 프로토콜
- FTP는 **아이디·패스워드가 암호화되지 않은 채 전송**되어 스니퍼(sniffer)에 쉽게 노출될 수 있으므로, 반드시 필요한 경우를 제외하고는 사용을 제한해야 함
- 안전한 암호화 통신이 필요하면 다음 서비스 이용을 권장:

| 대안 프로토콜 | 설명 |
|---|---|
| SFTP (SSH File Transfer Protocol) | SSH 기반의 파일 전송 프로토콜. 기본적으로 **22/tcp** 포트 사용 |
| FTPS (FTP over SSL/TLS) | SSL/TLS 기반의 파일 전송 프로토콜. 기본적으로 **990/tcp** 포트 사용 |

### 3-2. FTP 동작 모드 (능동/수동)

FTP는 명령을 전달하는 **제어 채널(Control Channel)**과 실제 파일 데이터를 전달하는 **데이터 채널(Data Channel)**을 구분해서 사용하며, 두 채널의 생성 방식에 따라 능동 모드/수동 모드로 나뉜다.

**능동 모드(Active Mode)** — FTP 클라이언트의 기본 동작 모드

| 채널 | 동작 |
|---|---|
| 제어 채널 | 클라이언트가 서버의 **21/tcp**로 접속하여 생성 후 명령 전달 |
| 데이터 채널 | 클라이언트가 `PORT` 명령으로 자신의 데이터 포트(예: 5001)를 서버에 알리면, **서버가 20/tcp에서 클라이언트의 1024/tcp 이상 포트로 접속**하여 데이터(파일, 파일 목록 등) 전달 |

!!! important "핵심"
    능동 모드는 서버가 클라이언트로 먼저 접속을 시도하는 구조라, 클라이언트 측에 방화벽이 있으면 데이터 채널 연결이 차단될 수 있다는 것이 실무 포인트입니다. 이 때문에 수동 모드(Passive Mode, 클라이언트가 양쪽 채널 모두를 먼저 여는 방식)가 대안으로 쓰입니다.

## 4. SNMP 프로토콜 심화

| 항목 | 내용 |
|---|---|
| 정의 | TCP/IP 기반 네트워크상의 각 호스트로부터 정기적으로 여러 관리 정보를 자동 수집하거나 실시간으로 상태를 모니터링·설정할 수 있는 서비스로, SNMP는 프로토콜일 뿐이며 이를 활용해 실제 네트워크 관리 정보를 얻기 위해서는 관련 프로그램(NMS 등)이 준비되어야 함 |
| 구성 요소 | 관리 시스템을 **Manager**, 관리 대상을 **Agent**라 부름. Manager는 Agent에 필요한 정보를 요청하는 주체, Agent는 관리 대상 시스템에 설치되어 정보를 수집하고 Manager에게 전달하는 모듈 |
| 계층·전송 | OSI 7계층의 Application 계층 프로토콜이며, 단순한 요청·응답 형식의 메시지로 교환되기 때문에 전송계층 프로토콜로 **UDP**를 사용 |
| 포트 | **Manager는 162/udp**(Trap 수신), **Agent는 161/udp**(Get/Set 요청 수신)를 이용 |
| 관련 프로그램 | MRTG(Multiple Router Traffic Grapher) — SNMP 기반의 장비 모니터링 프로그램으로, 벤더가 제공하는 SNMP MIB을 이용해 트래픽 사용량 등 다양한 정보 수집 |
| 보안 위협 | 편의성을 위해 설계되어 다양한 취약점 존재 — 서비스 거부 공격(DoS), 버퍼 오버플로우, 비인가 접근 등 |

**SNMP 메시지 동작 방식**: Manager(162/udp) → Get Request/Get Next Request/Set Request → Agent(161/udp) → Get Response, 그리고 Agent가 이상 상태를 감지하면 Manager에게 자발적으로 **Trap** 메시지를 전송

## 5. DHCP 프로토콜 심화

| 항목 | 내용 |
|---|---|
| 정의 | 동적으로 클라이언트의 네트워크 주소(IP)를 설정하기 위한 프로토콜 |
| 포트 | 67/udp(server), 68/udp(client) |
| 관련 명령어 | `ipconfig /release`(할당받은 IP 주소 해제) / `ipconfig /renew`(새로운 IP 주소를 DHCP 서버로부터 받음) |

**IP 할당 절차 (DORA)**

1. **DHCP Discover**: 클라이언트가 DHCP 서버를 찾기 위한 메시지로, 자신의 MAC 정보를 담아서 브로드캐스트
2. **DHCP Offer**: DHCP 서버가 클라이언트에게 IP 정보를 제공해주는 메시지
3. **DHCP Request**: 해당 IP를 사용하겠다고 서버에 요청하는 메시지. 서버가 Offer 메시지를 통해 주소를 제공하면 바로 설정하는 것이 아닌, 사용하겠다는 메시지를 다시 보냄
4. **DHCP Ack**: 서버는 해당 MAC과 IP 정보를 테이블에 저장하고, 다시 한번 할당된 주소정보를 클라이언트에게 전송. 클라이언트는 이 메시지를 받고 IP 정보를 설정

**DHCP Starvation 공격**

- DHCP 서버의 할당 가능한 IP를 모두 소진하게 만들어 IP 할당이 불가능하게 하는 공격
- 서로 다른 MAC 주소로 Discover 메시지를 대량으로 보내면 이에 대한 Offer가 올 것이고, Request 메시지까지 보낸 후에 실제로는 할당하지 않는(사용하지 않는) 방식으로 IP 풀을 고갈시킴
- **대응**: 스위치의 DHCP Snooping 적용, 포트별 최대 MAC 수 제한(Port Security)

## 6. 이메일(E-Mail) 보안

### 6-1. 이메일 시스템 구조

| 구성요소 | 역할 |
|---|---|
| MUA (Mail User Agent) | 메일 클라이언트. 사용자가 메일을 작성·확인하는 프로그램 (예: Outlook, Thunderbird) |
| MTA (Mail Transfer Agent) | 메일 서버 간 메일을 전송하는 프로그램 (예: Sendmail, Qmail, Postfix). 외부 메일 수신·내부 메일 수신 모두 SMTP로 처리 |
| MDA (Mail Delivery Agent) | MTA가 수신한 메일을 각 사용자 메일함(mailbox)에 파일 형태로 저장해주는 프로그램 (예: Procmail) |
| MRA (Mail Retrieval Agent) | 메일 클라이언트(MUA)가 요청하는 메일을 사용자 메일함에서 사용자에게 전달해주는 프로그램. MUA-MRA 간 통신은 **POP3 또는 IMAP** 프로토콜 기반 |

**이메일 시스템 동작 방식**

1. 사용자는 MUA로 메일을 작성 후, **SMTP 프로토콜**을 통해 클라이언트가 설정한 메일서버(MTA)로 전송
2. 메일 서버(MTA)는 메일 큐(mail queue)에 수신한 메일을 임시 저장한 후, 수신 메일을 분석하여 수신자가 자신이 아닌 메일주소라면 해당 주소의 메일 서버로 SMTP를 통해 전송하고, 수신자가 자신의 메일주소라면 MDA를 통해 각 사용자 메일함(mailbox)에 파일 형태로 저장
    - Sendmail 서버의 경우 메일 큐는 `/var/spool/mqueue` 디렉터리, 각 사용자 메일함은 `/var/spool/mail` 디렉터리에 위치
    - 수신자 메일주소의 메일 서버 확인 방법: 메일주소에 있는 도메인을 이용해 **MX(Mail Exchanger) 레코드**에 대한 DNS 질의를 수행
3. 사용자가 MUA를 통해 메일 확인(읽기 등)을 요청하면 MRA는 사용자 메일함의 메일을 **POP3 또는 IMAP** 프로토콜을 이용해 클라이언트에 전달

### 6-2. SMTP 메일 형식

- SMTP는 텍스트 기반의 프로토콜로 **봉투(Envelope)**와 **메시지(Message)** 정보를 주고받는다. 기본 포트는 **25/tcp**
- 통신 흐름: 연결 → `HELO`(발신 메일서버 도메인) → `MAIL FROM`(발신자 메일주소) → `RCPT TO`(수신자 메일주소) → `DATA`(메시지 헤더+바디 시작) → 메시지 전송 → `QUIT`
- 메시지는 헤더(Header: Received, Return-Path, From, To, Subject, Date 등)와 바디(Body: 메일 본문)로 구성

### 6-3. sendmail 보안 설정

[법·제도 파트](06-law-practice.md)의 sendmail access 파일(RELAY/DISCARD/REJECT) 및 [최종 총정리](07-final-summary.md)의 설정 파일 체계(sendmail.cf → access → access.db)를 함께 참고.

**access.db 생성 실무**: access 파일은 정책(룰) 설정을 위한 텍스트 파일로, 이를 실제 적용하려면 `makemap` 명령으로 `access.db` 데이터베이스 파일을 생성해야 한다.

```bash
makemap hash /etc/mail/access < /etc/mail/access
```

**릴레이 차단 동작 확인(실무 테스트)**: `telnet mail.domain.com 25` 로 접속 후 `MAIL FROM:` 명령에 차단 대상 주소(예: `attack@phishing.com`)를 입력하면 `553 5.3.0 ... 501[501 message] You are not allowed!!` 형태의 거부 응답을 받는다. 메일서버 로그(`/var/log/maillog` 등)에도 `reject=553 5.3.0 ...`, `REJECT` 처리 내역이 함께 기록된다.

### 6-4. 이메일 인증 기술(스팸 메일 방지 기술) — SPF

**SPF(Sender Policy Framework) 기술**: 수신한 메일이 발신자 메일주소의 정당한(인증된) 메일 서버로부터 온 메일인지 검증할 수 있는 이메일 인증 기술. 대다수 스팸(해킹) 메일 발신자가 발신자 메일주소를 조작(위조)하는 경우가 많다는 점에 착안하여 만들어짐. "발송자 메일서버 인증" 또는 "메일서버 등록제"라고도 표현

**동작 방식**

1. **발신측**: 발신 도메인의 관리자가 해당 도메인에서 사용하는 발신 메일서버의 IP 정보와, 수신 측 처리방식을 담은 **SPF 레코드**를 도메인의 **DNS 서버 TXT 레코드**에 공개적으로 등록
2. **수신측**: 수신 메일서버가 발신자 메일주소 도메인(MAIL FROM 정보)에 대한 SPF 레코드를 DNS로 조회(TXT 레코드 질의)한 후, 실제 메일을 발송한 메일서버의 IP가 조회된 SPF 레코드에 등록된 서버인지 여부와 처리방식에 따라 수신 여부를 결정

**SPF 레코드 형식**: 버전(Version) + 하나 이상의 한정자(Qualifier)와 메커니즘(Mechanism)의 조합으로 이루어진 텍스트 (`v=spf1 ip4:211.252.150.8 include:_SPFinclu.kisa.or.kr -all`)

| 한정자(Qualifier) | 의미 |
|---|---|
| `+` | 인증 통과(Pass) — 메커니즘과 일치하면 메일 통과. 한정자 미지정 시 기본 적용값 |
| `-` | 인증 실패/심각한 실패(Fail, Hard Fail) — 메커니즘과 일치하면 메일을 거부(차단) |
| `~` | 가벼운 인증 실패(Soft Fail) — 일치하면 수신측 메일서버 정책에 따라 허용 여부 판단(의심 메일로 표시될 수 있음) |
| `?` | 중립(Neutral) — 인증 여부에 대한 판단 정보 없음 |

**메커니즘(Mechanism)**: `ip4`/`ip6`(IPv4/IPv6 주소 또는 대역 지정) · `include`(지정한 도메인에 있는 SPF 레코드 정보를 참조) · `all`(모든 주소 의미, 일반적으로 레코드 가장 마지막에 위치하여 이전 메커니즘에 일치하지 않는 나머지 모든 주소를 의미)

!!! tip "핵심"
    `-all`은 "SPF 레코드에 등록되지 않은 서버에서 온 메일은 모두 거부하라"는 뜻이고, `~all`은 "등록되지 않은 서버에서 온 메일은 수신측 정책에 맡긴다(Soft Fail)"는 뜻입니다. 이 차이를 구분하는 문제가 출제될 수 있습니다.

## 7. 데이터베이스 보안

### 7-1. 데이터베이스 보안 위협

| 위협 | 정의 | 예시 |
|---|---|---|
| 집성(Aggregation) | 낮은 보안 등급의 정보 조각들을 조합하여 높은 보안 등급의 정보를 알아내는 것. 개별 데이터 항목보다 종합 정보의 보안 등급이 높은 경우 심각한 기밀 정보 유출 문제 발생 | 보안 등급이 낮은 각 영업점의 매출액을 모두 조합하여 보안 등급이 높은 회사의 총매출액을 계산 |
| 추론(Inference) | 보안 등급이 없는 일반 사용자가 보안으로 분류되지 않은 정보를 정당하게 접근하여 기밀 정보를 유추해내는 행위. 주로 통계(집계) 정보로부터 발생하기 때문에 통계 정보로부터 개개의 개체에 대한 정보를 추적하지 못하도록 해야 함 | 어떤 직원이 공개된 정보인 계약직 직원의 평균 연봉과 인원수를 질의했을 때, 계약직 직원 수가 1명이라면 평균(average)·총계(sum)라는 통계 질의만으로도 민감정보인 계약직 직원의 연봉을 추론 가능 |

**키워드**: 집성 = "조합", 추론 = "유추"

### 7-2. 데이터베이스 보안 통제

| 통제 | 설명 |
|---|---|
| 접근 통제(제어) | 데이터베이스 사용자가 가진 접근 권한의 범위 내에서 데이터 접근을 허용하는 기술적인 방법. DBA는 개별 사용자 또는 역할/그룹별로 접근 가능한 데이터, 접근 수준(필드/레코드 수준), 허용할 작업(CRUD: 읽기/변경/삽입/삭제)을 결정 |
| 추론 통제(제어) | 통계 정보 등 간접적으로 노출된 데이터를 통해서 민감·기밀 데이터가 유추되어 공개되는 것을 방지. 완벽한 해결책은 없지만 일반적 방지 방법: 허용 가능한 질의를 제한 / 질의의 응답으로 제공되는 데이터를 한정 / 데이터가 숫자인 경우 반올림하거나 일관성 없는 질의 결과를 제공 |

### 7-3. 데이터베이스(MySQL) 취약점 점검 실무

MySQL은 오라클(Oracle)에서 관리·배포하는 오픈소스 관계형 DBMS로 가장 많은 시장점유율을 차지한다. 최초 설치 시 `mysql`이라는 시스템 데이터베이스가 생성되며, 다음과 같은 주요 기본 테이블을 갖는다.

| 테이블 | 정보 |
|---|---|
| user | 전체 데이터베이스에 적용되는 사용자 정보와 권한 정보 |
| host | 호스트 전체에 대한 데이터베이스 접근 권한 정보 |
| db | 각각의 데이터베이스에 대한 접근 권한 정보 |
| table_priv | 테이블에 대한 접근 권한 정보 |
| columns_priv | 테이블의 컬럼에 대한 접근 권한 정보 |

**취약점 점검 절차 — 디폴트 관리자(root) 패스워드 변경**

1. mysql 디폴트 설치 시 데이터베이스 관리자(root) 패스워드가 **비어있는(NULL) 상태**로 설정됨 — `select host,user,password from user;`로 확인 가능. `host` 필드의 `%`는 로컬 호스트를 제외한 모든 호스트를 의미
2. `update user set password=password('새비밀번호') where user='root';` 구문으로 관리자(root) 계정의 패스워드를 변경(입력한 패스워드를 그대로 저장하지 않고 해시로 암호화하여 저장)
3. `flush privileges;` 명령으로 변경 사항을 즉시 반영 — 사용자 정보의 추가(insert)·변경(update)·삭제(delete) 등을 수행했을 때 반영을 위해 사용

!!! important "핵심"
    "mysql DB 디폴트 설치 시 root 계정의 패스워드가 비어있다(NULL)"는 것이 핵심 취약점입니다. 점검 시 `select host,user,password from user;`로 빈 패스워드 계정을 확인하고, `update ... password()` + `flush privileges`로 조치하는 순서를 기억하세요.

## 8. 클라우드 컴퓨팅 보안

### 8-1. 개요 및 특징

- **법적 정의** (클라우드컴퓨팅 발전 및 이용자 보호에 관한 법률): 집적·공유된 정보통신기기, 정보통신설비, 소프트웨어 등 정보통신자원을 이용자의 요구나 수요 변화에 따라 정보통신망을 통하여 유동적으로 이용할 수 있도록 하는 정보처리체계
- 이용자가 필요한 만큼 IT자원(서버, 스토리지, 네트워크, 애플리케이션 등)을 빌려서 사용하고, 서비스 부하에 따라 실시간 확장성을 지원받으며, 사용한 만큼 비용을 지불하는 컴퓨팅 환경
- 핵심 기술은 **가상화(Virtualization)**: 물리적 IT 자원을 동시에 다수의 논리적 IT 자원으로 사용할 수 있는 기술. 대상에 따라 데스크톱 가상화, 애플리케이션 가상화, 스토리지 가상화, 서버 가상화, 네트워크 가상화로 구분

### 8-2. 서비스 모델(Delivery Model)

전통적 온프레미스(On-Premise, IT자원을 직접 소유·운영하는 방식) 환경과 비교해, 이용자가 관리하는 범위(You Manage)와 벤더가 관리하는 범위(Managed by vendor)가 서비스 모델별로 다르다.

| 모델 | 정의 | 예시 |
|---|---|---|
| IaaS (Infrastructure as a Service) | 이용자에게 서버·스토리지·네트워크 등의 하드웨어 인프라 자원만을 사용량 기반으로 제공. 기존 물리적으로 구축했던 인프라 자원을 가상화 기술로 신속하게 할당받아 사용 (실시간 확장성) | AWS S3/EC2 |
| PaaS (Platform as a Service) | 이용자에게 애플리케이션을 개발·테스트·실행하는 데 필요한 운영체제(OS), 개발 환경 플랫폼(WEB/WAS/DB 등), 개발 언어 프레임워크를 제공. 서버 구매/임대, OS·미들웨어·프레임워크 설치 등 선행 작업 시간·비용을 줄이고 서비스 개발에 집중 가능 | MS Azure, Google App Engine, Oracle PaaS |
| SaaS (Software as a Service) | 이용자에게 클라우드 환경에서 동작하는 애플리케이션/소프트웨어를 제공 | Dropbox, 네이버 N 클라우드, 구글 드라이브, 세일즈포스닷컴 CRM |

### 8-3. 클라우드 기반 보안 서비스 — SECaaS (Security as a Service)

- SaaS의 한 종류로 '클라우드 기반 보안' 또는 '보안 클라우드'라고도 불림
- 전통적인 온프레미스 형태의 기업 내 구축형 보안 솔루션 방식이 아닌, 클라우드(인터넷)를 통해 주문형(On-Demand) 방식으로 제공하는 보안 서비스 모델
- 초기 투자 비용 없이 클라우드를 통해 보안 서비스를 이용, 사용한 만큼 비용을 지불(경제적), 최신 위협에 민첩하게 대응하는 전문가 집단의 보안 서비스 제공

**보안 서비스 분야 (클라우드 보안 연합, CSA: Cloud Security Alliance 정의)**

| # | 분야 | 설명 |
|---|---|---|
| 1 | 식별·접근 관리(IAM) | 인증, 신원보증, 접근 권한이 있는 사용자 관리를 포함한 관리 및 접근제어 제공 |
| 2 | 데이터 유출·손실 방지(DLP) | 이동 및 사용 중인 데이터의 보안 및 모니터링, 보안 검증 |
| 3 | 웹 보안(Web Security) | 클라우드 서비스 공급자를 통해 웹 트래픽을 프록시 처리하여 애플리케이션 서비스를 실시간으로 보호 |
| 4 | 이메일 보안(Email Security) | 인바운드·아웃바운드 Email을 제어하고 피싱 및 악의적인 첨부 파일과 스팸으로부터 조직을 보호 |
| 5 | 보안 감사(Security Assessments) | 업계 표준을 기반으로 클라우드 서비스에 대한 제3자 감사 |
| 6 | 침입 관리(Intrusion Management) | 패턴 인식을 통하여 통계적으로 이벤트를 감지, 침입 시도 방지 또는 탐지를 통해 관리 |
| 7 | 보안정보 및 이벤트 관리(SIEM) | 보안 로그 및 이벤트 정보에 대한 상관관계 및 실시간 분석 |
| 8 | 암호화(Encryption) | 해독할 수 없도록 데이터를 암호화 |
| 9 | 업무 연속성과 재난 복구(BCDR) | 서비스 중단 시 운영의 탄력성을 보장하도록 설계된 조치 |
| 10 | 취약점 검사(Vulnerability Scanning) | 공용 네트워크를 통해 대상 인프라 또는 시스템의 취약점을 검사 |
| 11 | 지속적인 모니터링(Continuous Monitoring) | 조직의 현재 보안 상태를 나타내는 지속적인 위험 관리 기능 수행 |
