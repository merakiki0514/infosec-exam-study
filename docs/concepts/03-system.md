# 파트 3. 시스템 보안

시스템 보안은 리눅스/윈도우 보안 설정, 로그 분석, 소프트웨어 취약점을 다룹니다. 실무형 문제에서 직접 명령어와 설정값을 작성해야 하므로 정확한 암기가 필요합니다.

## 1. 리눅스 핵심 보안 설정

> 출제 이유: 리눅스 보안 설정 파일의 경로와 파라미터, 명령어를 정확히 알아야 실무형 문제를 풀 수 있습니다.

### 1-1. 계정 및 패스워드 보안

| 항목 | 파일/설정 |
|---|---|
| 패스워드 최소 길이 설정 (24년도 2회) | 파일: `/etc/login.defs` / 설정: `PASS_MIN_LEN 8` |
| 패스워드 정책 주요 파라미터 | `PASS_MAX_DAYS`: 최대 사용 기간 / `PASS_MIN_DAYS`: 최소 사용 기간 / `PASS_MIN_LEN`: 최소 길이 / `PASS_WARN_AGE`: 만료 경고 일수 |
| /etc/passwd 구조 (26년도 1회) | `username:x:UID:GID:comment:home:shell` / x → 패스워드가 /etc/shadow에 저장됨을 의미 |
| /etc/shadow 구조 (25년도 4회) | `username:$ID$salt$hash:lastchg:min:max:warn:inactive:expire` / $ID: 해시 알고리즘 식별자 ($1=MD5, $5=SHA-256, $6=SHA-512) |
| 암호화 패스워드 파일 (25년도 2회) | `/etc/shadow` — 암호화된 패스워드 저장, root만 읽기 가능 |

### 1-2. 리눅스 핵심 로그 파일 & 명령어

| 명령어/파일 | 설명 |
|---|---|
| utmp (24년도 4회) | 현재 로그인 중인 사용자 정보 (who, w 명령이 참조) |
| wtmp (24년도 4회) | 로그인·로그아웃 이력 전체 기록 (last 명령이 참조) |
| lastlog (24년도 4회) | 각 계정의 마지막 로그인 정보 (lastlog 명령이 참조) |
| lastb (25년도 1회) | 로그인 실패 기록 (/var/log/btmp 파일 참조) |
| lastcomm (25년도 2회) | 실행된 명령어 이력 확인 (process accounting 기반) |
| lsof (25년도 1회) | List Open Files — 시스템의 모든 프로세스가 열어놓은 파일·소켓 정보 확인. 악성 프로세스의 열린 포트 확인에 활용 |
| /var/log/messages | 시스템 전반의 로그. Promiscuous Mode 진입 로그 등 기록 |
| /var/log/secure | 인증·권한 관련 로그 (SSH 접속, su 명령 등) |
| /var/log/syslog | Ubuntu/Debian 계열 시스템 로그 (/var/log/messages 대응) |

!!! important "핵심"
    lastb = 실패 로그인 / lastlog = 마지막 로그인 / wtmp = 전체 이력 / utmp = 현재 — 4가지 구분이 자주 출제됩니다.

### 1-3. 리눅스 보안 실무 설정 (25년도 4회)

| 설정 항목 | 방법 |
|---|---|
| 세션 타임아웃 | `export TMOUT=600` → `/etc/profile` 또는 `/etc/bashrc`에 추가 (600초 = 10분) |
| root 콘솔 접근 제한 | `/etc/securetty` — root가 로그인 가능한 터미널(tty) 목록 관리. 불필요한 항목 제거 |
| 파일 권한 설정 | 644: 일반 설정 파일 (소유자 읽기/쓰기, 그룹/기타 읽기만) / 400: 패스워드·인증 관련 파일 (소유자 읽기만) |
| World-writable 파일 탐지 | `find / -type f -perm -2` (-2 = other에 쓰기 권한 있는 파일) |
| 기본 umask 설정 | `umask 022` → 생성 파일 기본 권한 644, 디렉터리 755 |
| 불필요 서비스 비활성화 | `systemctl disable [서비스명]` 또는 `chkconfig [서비스명] off` |

### 1-4. 쉘(Shell) 정의와 기능 (25년도 1회)

| 항목 | 내용 |
|---|---|
| 정의 | 사용자와 커널(운영체제) 사이에서 명령어를 해석해 주는 대화형 사용자 인터페이스 (명령어 해석기) |
| 종류 | sh, bash (가장 일반적), csh, ksh, zsh 등 |

**쉘의 주요 기능 8가지**

1. 자체 내장 명령어 제공 (cd, echo, export 등)
2. 리다이렉션(Redirection): 표준 입력/출력/오류 방향 재지정 (`>`, `>>`, `<`, `2>`)
3. 파이프라인(Pipeline): 명령어 간 데이터 전달 ( `|` 연산자 )
4. 와일드카드(Wildcard): 파일명 패턴 매칭 (`*`, `?`, `[ ]`)
5. 조건부/무조건부 명령열 작성 (if-else, for, while 등)
6. 서브쉘 생성: 현재 쉘 내에서 하위 쉘 프로세스 생성
7. 백그라운드 프로세스 처리 (`&` 연산자)
8. 쉘 스크립트 작성 및 실행

### 1-5. PATH 환경변수 취약점 (root 홈·패스 디렉터리 권한)

| 항목 | 내용 |
|---|---|
| 취약 원리 | root 계정의 PATH 환경변수에 `.`(현재 디렉터리 지칭)이 포함되어 있으면, root 계정으로 접속한 관리자가 의도하지 않은 현재 디렉터리에 있는 명령어가 실행될 수 있음. `.`이 `/usr/bin`, `/bin`, `/sbin` 등 정상 명령어들이 있는 디렉터리보다 PATH 환경변수에 우선하여 있으면, 현재 디렉터리에 변조된 명령어(예: `ls`)를 악의적으로 삽입해 명령어 입력 시 변조된 명령어가 실행될 수 있음 |
| 점검 파일 | `/etc/profile`(모든 사용자 로그인 시 적용) 또는 root 홈 디렉터리의 `.bash_profile` |
| 취약 설정 예시 | `PATH=.:$PATH` (`.`이 맨 앞 또는 중간에 위치 → 취약) |
| 조치 방법 | PATH 환경변수에서 `.`을 제거하거나, 반드시 필요하다면 PATH 문자열의 **맨 마지막으로 이동** |

!!! tip "시스템에서 명령어를 찾는 절차"
    1. PATH 환경변수에 설정된 경로를 순서대로 탐색하며 명령어를 찾는다.
    2. 명령어가 있으면 실행 권한을 확인한다.
    3. 실행 권한이 있다면 명령어를 실행시킨 사용자 ID(UID)로 명령어를 실행한다.
    4. 실행파일에 setuid/setgid가 설정되어 있다면 소유자/소유그룹 권한으로 명령어를 실행한다.

### 1-6. /etc/passwd 파일 구조 심화

```
[user_account]:[user_password]:[user_ID]:[group_ID]:[comment]:[home_directory]:[login_shell]
       ①              ②            ③          ④          ⑤            ⑥                ⑦
```

| 필드 | 항목 | 설명 |
|---|---|---|
| ① | user_account | 사용자 계정명. root 계정은 시스템에 대한 총괄 권한을 가지므로 원격 접속을 금지하는 것이 보안상 안전(일반 계정으로 로그인 후 `su`로 전환하여 사용) |
| ② | user_password | 사용자 패스워드. `x`의 의미는 패스워드를 사용하지 않는다는 것이 아니라 **shadow 패스워드를 사용한다**는 의미 |
| ③ | UID | 사용자 ID. **root(관리자) 계정의 UID는 0**으로 부여됨. UID는 중복 사용될 수 있으며 동일 UID가 부여된 계정은 서로 같은 권한을 가짐 → **임의로 생성된 일반 계정에 UID가 0으로 부여되어 있다면 root 권한 탈취를 위한 행위로 의심**해야 함 |
| ④ | GID | 사용자 기본 그룹 ID. GID도 UID와 동일하게 중복 부여될 수 있으므로 임의로 생성된 그룹에 GID가 0으로 부여되어 있는지 점검해야 함 |
| ⑤ | comment | 사용자 이름 등 실명 정보 |
| ⑥ | home_directory | 홈 디렉터리. 로그인 성공 후 위치할 디렉터리 (root는 `/`, 일반 사용자는 보통 `/home` 하위) |
| ⑦ | login_shell | 로그인 쉘. 리눅스 기본은 bash. 로그인이 불필요한 계정(시스템·애플리케이션 계정, 예: apache, nginx)은 **`/sbin/nologin` 또는 `/bin/false`로 설정**하여 공격자에 의한 불법적 시스템 접근에 악용되지 않도록 해야 함 |

!!! important "핵심 실무 점검 포인트"
    root 이외의 계정에서 UID 또는 GID가 0으로 설정된 경우, 권한 탈취를 위해 공격자가 생성한 계정일 가능성이 높으므로 **주기적으로 UID/GID가 0인 일반 사용자 계정이 있는지 점검**해야 합니다. 서비스 계정의 `login_shell`이 `/bin/bash` 등 실제 로그인 가능한 쉘로 설정되어 있다면 `/sbin/nologin`으로 변경을 권고하는 실무형 문제로 출제될 수 있습니다.

### 1-7. /etc/shadow 파일 구조 심화

```
[user_account]:[encrypted_password]:[last_change]:[minlife]:[maxlife]:[warn]:[inactive]:[expires]
       ①                  ②                ③            ④          ⑤        ⑥            ⑦          ⑧
```

| 필드 | 항목 | 설명 |
|---|---|---|
| ② | encrypted_password | 암호화된 패스워드. `$ID$salt$hash` 형식 ([1-1](#1-1-계정-및-패스워드-보안) 참고) |
| ③ | last_change | 마지막으로 패스워드를 변경한 날(1970.1.1 기준 일수로 표시) |
| ④ | minlife (PASS_MIN_DAYS) | 패스워드 **최소 사용기간** — 마지막 변경 이후부터 패스워드를 다시 변경할 수 없는 일수. 최소 사용기간이 없으면 사용자가 방금 변경한 패스워드를 바로 재변경(A→B→A)해 과거 암호 기억을 무력화하고 익숙한 패스워드를 재사용하는 문제가 있으므로 **1일(1주)로 설정 권장** |
| ⑤ | maxlife (PASS_MAX_DAYS) | 패스워드 **최대 사용기간** — 이 기간이 지나면 패스워드 만료. 최대 사용기간을 설정하지 않으면 패스워드 유출 시 공격자의 지속적인 접근이 가능해지므로 **90일(12주)로 설정 권장** |

!!! tip "핵심 목적"
    minlife·maxlife 설정의 목적은 "패스워드가 유출되어도 지속적으로 해당 계정에 접근하지 못하게 하는 것"입니다. 서술형으로 "패스워드 최소/최대 사용기간을 설정하는 이유"가 출제될 수 있습니다.

### 1-8. 파일시스템 inode 구조 (디지털 포렌식 연계)

| 속성 | 설명 |
|---|---|
| inode number | 파일시스템 내에서 해당 파일을 식별하기 위한 고유 식별자. 파일시스템별로 고유한 값이므로 **동일 파일시스템 내에서만 하드 링크 가능** |
| 파일타입 | 일반(정규)파일, 디렉터리, 장치파일 등 파일 유형 |
| 접근권한 | 파일에 대한 접근권한(rwx) |
| link count | 해당 inode를 참조하는 하드 링크 개수 |
| 소유자/소유그룹 | 파일의 소유자(UID)/소유그룹(GID) |
| 파일크기 | 파일의 크기 |
| **MAC Time** | ① Modification Time(파일 **내용**을 마지막으로 수정한 시간) ② Access Time(파일을 마지막으로 **접근**한 시간) ③ Change Time(파일 **속성**을 마지막으로 변경한 시간 — 소유자·접근권한 등 inode 정보가 변경되면 갱신) |

- 특정 파일의 inode 정보는 리눅스 `stat` 명령으로 확인 (`stat /etc/passwd`)
- **침해사고 발생 시 피해 시스템의 무결성 확인을 위한 타임라인 분석**을 수행하며, 이때 inode 구조체의 MAC Time을 점검한다

**하드 링크(Hard Link) vs 심볼릭 링크(Symbolic Link)**

| 구분 | 설명 |
|---|---|
| 하드 링크 | 기존 파일과 **동일한 inode number**를 갖는 파일을 생성하여 접근하는 방식. 동일 파일시스템 내에서만 가능하며, 디렉터리는 하드 링크 불가능. 생성 시 해당 inode의 link count가 1 증가하며, 파일 삭제 시 link count를 1 감소시킨 후 0이 되었을 때 실제 데이터가 삭제됨(inode를 참조하는 파일이 남아있으면 삭제되지 않음) |
| 심볼릭 링크 | 윈도우의 바로가기 아이콘처럼 원본 파일의 경로를 가리키는 별도의 작은 파일. 파일·디렉터리 모두 가능 |
| 명령 | `ln source target` (하드 링크) / `ln -s source target` (심볼릭 링크) |

### 1-9. 파일 권한 실무 — find -perm 옵션

| 명령 | 의미 |
|---|---|
| `find . -type f -perm 600` | `-`(하이픈) 없이 사용 — 권한이 **정확히** 600(rw-------)과 **일치**하는 파일만 검색 |
| `find . -type f -perm -600` | `-`(하이픈)을 붙이면 — 소유자(User)에 rw(6) 권한을 **포함**하고 있는 파일 검색(다른 권한 무관) |
| `find . -type f -perm -2` | 기타 사용자(Others)에 쓰기 권한(2)을 포함하는 파일 → world-writable 파일 탐지 |
| `find . -type f -perm -22` | 소유그룹(Group)과 기타 사용자(Others) 모두에 쓰기 권한(2)을 포함하는 파일 |
| `find . -type f -perm -222` | 소유자·소유그룹·기타 사용자 **모두**에 쓰기 권한(2)을 포함하는 파일 |

### 1-10. PAM (Pluggable Authentication Modules) 구조 심화

| 항목 | 내용 |
|---|---|
| 정의 | 리눅스 시스템 내에서 사용되는 각종 애플리케이션 인증을 위해 제공되는 다양한 인증용 라이브러리. 프로그램 개발 시 인증 모듈을 별도 개발하지 않고 플러그인(plug-in) 방식으로 PAM을 사용함으로써 인증 방식·정책의 유연성과 중앙 통제가 가능 |
| `/etc/pam.d/` | PAM 라이브러리를 이용하는 각 응용 프로그램(서비스)의 설정 파일이 위치. 설정파일명은 응용 프로그램(서비스)명과 동일(예: login, sshd, su-l) |
| `/lib/security` 또는 `/usr/lib/security` | PAM 라이브러리가 제공하는 다양한 인증 모듈(`.so` 파일, 예: pam_tally2.so, pam_nologin.so)이 위치 |
| `/etc/security` | PAM 모듈 실행에 필요한 추가 설정 파일(access.conf, limits.conf, time.conf 등)이 위치 |

**PAM을 사용한 인증 절차**: ① login·telnet·ftp 등 각 프로그램이 인증이 필요한 부분에서 PAM 라이브러리를 호출 → ② PAM 라이브러리가 해당 프로그램의 PAM 설정 파일(`/etc/pam.d/`)을 참조하여 등록된 여러 PAM 모듈을 수행 → ③ 응용 프로그램은 반환된 결과를 이용하여 인증 여부를 결정

### 1-11. 로그인 실패/성공 로그 파일 (Linux vs Unix·SunOS)

리눅스와 Unix(SunOS) 계열은 로그 파일 경로와 형식이 다르므로 구분해서 암기해야 합니다.

| 구분 | Linux | Unix(SunOS) |
|---|---|---|
| 마지막 로그인 성공 기록 | `/var/log/lastlog` (binary) — `lastlog` 명령으로 확인 | `/var/adm/lastlog` (binary) — `finger` 명령으로 확인 |
| 로그인 실패 기록 | `/var/log/btmp` (binary, 모든 실패 기록) — `lastb` 명령으로 확인 | `/var/adm/loginlog` (**text 파일**, vi 등으로 직접 확인 가능) — **5회 이상 연속 실패 시에만** 로그 생성 |
| 로그인 성공 전체 이력 | `/var/log/wtmp` (binary) — `last` 명령으로 확인 | 동일 |

**실무 명령어**: `lastlog -u <계정명>`(특정 계정의 최근 접속 기록), `lastlog -t <일수>`(해당 일수 이내 접속 기록), `lastb <계정명>`(특정 계정의 로그인 실패 기록), `last reboot | head -5`(재부팅 이력 확인)

| 항목 | 내용 |

| 조치 방법 | 불필요한 기본 공유(C$, D$, ADMIN$ 등) 제거 |

## 3. 주요 보안 취약점

> 출제 이유: 유명 취약점은 CVE 수준에서 개념과 조치 방법을 물어봅니다. 특히 HeartBleed는 조치를 시스템적/서비스적으로 구분하여 서술해야 합니다.

### 3-1. HeartBleed (하트블리드) (24년도 2회)

| 항목 | 내용 |
|---|---|
| CVE | CVE-2014-0160 |
| 영향 대상 | OpenSSL 1.0.1 ~ 1.0.1f (TLS Heartbeat 확장 구현 취약점) |
| 원리 | TLS Heartbeat 요청에 포함된 메시지 길이를 검증하지 않아, 서버 메모리에서 최대 64KB의 데이터를 읽어내는 메모리 과다 읽기(Buffer Over-Read) 취약점 |
| 유출 정보 | 서버의 SSL 개인키, 사용자 세션 토큰, 패스워드 등 메모리 내 민감 정보 |

**조치 방법**

| 조치 구분 | 내용 |
|---|---|
| 시스템적 조치 | 취약한 OpenSSL 라이브러리를 취약점이 패치된 버전(1.0.1g 이상)으로 업데이트 |
| 서비스적 조치 1 | 서버 SSL/TLS 개인키가 유출되었을 가능성이 있으므로 인증서 재발급 검토 |
| 서비스적 조치 2 | 조치 완료 후 사용자들의 비밀번호 재생성 유도 → 탈취된 계정을 통한 추가 피해 방지 |

### 3-2. 버퍼 오버플로우 (Buffer Overflow) (25년도 2회)

| 항목 | 내용 |
|---|---|
| 정의 | 연속된 메모리 공간을 사용하는 프로그램에서 할당된 메모리의 범위를 넘어선 위치에 자료를 읽거나 쓰려고 할 때 발생. 프로그램의 오작동을 유발시키거나, 악의적인 코드를 실행시킴으로써 공격자가 프로그램을 통제할 수 있는 권한을 획득하게 됨 |
| 스택(Stack) 버퍼 오버플로우 | 스택은 함수 처리를 위해 지역변수 및 매개변수가 위치하는 메모리 영역. 스택에 할당된 버퍼들이 문자열 처리 등에 의해 정의된 버퍼의 한계치를 넘는 경우, 버퍼 오버플로우가 발생하여 복귀 주소(Return Address)를 변경하고 공격자가 원하는 임의의 코드를 실행 |
| 힙(Heap) 버퍼 오버플로우 | 힙은 사용자가 동적으로 할당하는 메모리 영역(`malloc()` 등 메모리 할당 함수 이용). 힙에 할당된 버퍼들에 문자열 등이 저장될 때, 최초 정의된 힙의 메모리 사이즈를 초과하여 문자열 등이 저장되는 경우 버퍼 오버플로우가 발생하여 데이터와 함수 주소 등을 변경하여 공격자가 원하는 임의의 코드를 실행 |
| 위험 함수 (취약) | `strcpy(char *dst, const char *src)`: src 문자열의 길이를 체크하지 않으므로 dst 버퍼를 초과하는(오버플로우) 결과 발생 가능. 그 외 `strcat()`, `gets()`, `sprintf()`, `scanf()` — 길이 검사 없음 |
| 안전한 대안 함수 | `strncpy(char *dst, const char *src, size_t len)`: src 문자열의 len 만큼을 dst 버퍼에 저장 — 길이를 제한하므로 오버플로우에 안전. 그 외 `strncat()`, `fgets()`, `snprintf()` |
| C언어 문자열 처리 | C언어에서 문자열은 null 문자(`0x00`)로 문자열의 끝을 표현. 예: "ABCD"(4글자)는 실제로 "ABCD\0"의 5개 문자로 저장됨 → 버퍼 크기를 계산할 때 null 문자 자리를 빠뜨리면 오프바이원(off-by-one) 오버플로우가 발생할 수 있음 |

**버퍼 오버플로우 방어 기법**

- 스택 카나리(Stack Canary): 리턴 주소 전에 랜덤 값을 배치하여 덮어쓰기 감지
- ASLR (Address Space Layout Randomization): 메모리 주소를 무작위 배치하여 공격 어렵게 함
- NX/DEP (No-Execute / Data Execution Prevention): 스택·힙 영역에서 코드 실행 불가
- 안전한 라이브러리 함수 사용

## 4. 디지털 포렌식 & 보안 도구

**디지털 포렌식 5단계 절차**

1. **사전 준비(Preparation)**: 포렌식 도구 준비 및 사전 테스트(대표 도구: EnCase, FTK)
2. **증거 수집/획득(Acquisition)**: 현장의 디지털기기로부터 무결성을 보장하면서 디지털 증거를 수집 — 저장매체 이미징(imaging), 복제(cloning), 복사(copy) 등
3. **보관 및 이송(Preservation)**: 수집한 디지털 증거물을 연계 보관성 원칙을 만족시키며 이송·보관 (증거물 포장, 이송, 보관)
4. **조사 및 분석(Examination & Analysis)**: 수집된 디지털 증거물을 조사·분석 (데이터 복구, 데이터 추출·분류, 증거 검색)
5. **보고서 작성(Reporting)**: 조사·분석 결과를 이용해 법정에 제출할 보고서 작성

**안티 포렌식(Anti-Forensic)**: 디지털 데이터를 조작·삭제 또는 난독화하여 디지털 포렌식을 방해하는 행위

| 유형 | 설명 |
|---|---|
| 데이터 은폐(Data Hiding) | 데이터 암호화, 스테가노그래피(Steganography, 이미지·음향 파일 등에 정보를 은닉하는 기법) 등 |
| 데이터 파괴(Data Wiping) | 디스크 와이핑(Disk Wiping): 디스크에 저장된 데이터를 0, 1 또는 랜덤한 값으로 여러 번 덮어써서 데이터를 복구할 수 없도록 만드는 기법 |

| 수행 절차(간략) | 증거 식별 → 수집(이미징) → 보관 → 분석 → 보고 |

## 5. 접근통제 모델 (필수 암기)

> 출제 이유: 매 회차 출제되는 핵심 이론입니다. 3가지 모델의 차이를 명확히 설명할 수 있어야 합니다.

### 5-1. 접근통제 3가지 모델 (24년도 4회)

| 모델 | 정의 / 특징 |
|---|---|
| DAC (임의적 접근통제) / Discretionary Access Control | 주체 또는 그들이 속한 그룹의 ID에 근거하여 객체 접근 제한 / 자원 소유자가 접근 권한을 임의로 설정 가능 / 유연하지만 권한 관리가 분산되어 통제 어려움 / 예: 리눅스 파일 권한 (chmod), ACL |
| MAC (강제적 접근통제) / Mandatory Access Control | 객체의 비밀성 등급과 주체의 허가 등급(보안 레이블)에 근거하여 접근 강제 제한 / 중앙에서 관리자가 정책 설정, 소유자도 임의 변경 불가 / 군사·정부 기관에 적합 / 예: SELinux |
| RBAC (역할 기반 접근통제) / Role-Based Access Control | 사용자의 역할(Role)에 따라 접근 권한 부여 / 역할 변경 시 자동으로 권한 변경, 대규모 조직에서 관리 효율 높음 / 예: ERP 시스템의 부서별 권한 |

!!! important "핵심"
    DAC=소유자 자유 설정, MAC=보안 등급 강제, RBAC=역할별 권한 — 이 3가지 핵심 차이를 한 문장씩 서술할 수 있어야 합니다.

### 5-2. 추가 접근통제 모델

| 모델 | 설명 |
|---|---|
| ABAC (속성 기반 접근통제) | 사용자·자원·환경의 다양한 속성(시간, 위치, 부서 등)을 조합하여 접근 제어. 가장 세밀한 제어 가능 |
| Bell-LaPadula 모델 | 기밀성 중심 MAC 모델. No Read Up(상위 등급 읽기 금지), No Write Down(하위 등급 쓰기 금지) |
| Biba 모델 | 무결성 중심 MAC 모델. No Write Up(상위 등급 쓰기 금지), No Read Down(하위 등급 읽기 금지) |

## 6. 보안 관제 솔루션

### 6-1. SOAR (24년도 1회)

| 항목 | 내용 |
|---|---|
| 정의 | Security Orchestration, Automation and Response. 보안 운영의 자동화·오케스트레이션·대응을 통합하는 플랫폼 |
| 특징 | SIEM보다 진보된 형태. AI/빅데이터 기반 지능형 공격 탐지 및 자동 대응 |
| SIEM과의 차이 | SIEM: 로그 수집·분석·탐지 중심 / SOAR: 탐지 + 자동화된 대응(Playbook) 수행 |

### 6-2. SIEM (26년도 1회)

| 항목 | 내용 |
|---|---|
| 정의 | Security Information and Event Management. 다양한 보안 장비·서버의 로그와 이벤트를 실시간으로 수집·상관 분석하여 보안 위협을 통합 관제하는 시스템 |
| 기능 | 로그 통합 수집 / 실시간 모니터링 / 상관 분석(Correlation) / 경보 / 보고서 생성 |
| 대표 제품 | IBM QRadar, Splunk, ArcSight, LogRhythm 등 |

### 6-3. 보안 관제 구성요소 3가지 (25년도 2회)

| 구성요소 | 역할 |
|---|---|
| 에이전트 (Agent) | 보안 장비·서버·네트워크 장비에 설치. 해당 시스템의 로그 정보를 실시간으로 중앙관제센터에 전송 |
| 정보수집 서버 (Information Collection Server) | 에이전트에서 전송된 대량의 정보를 수집·처리하여 DB에 저장 |
| 통합관제용 서버 (SMS, Security Monitoring System) | 이벤트 로그 종합 분석. 다양한 정보를 상관 분석하여 관제 담당자 지원 및 경보 발령 |

### 6-4. 보안 솔루션 종류 전체 정리 (단답형 빈출)

시험에서 "OO을 수행하는 보안 솔루션은?" 형태로 약어·풀네임을 묻는 단답형 문제가 자주 출제됩니다. 카테고리별로 묶어서 암기하세요.

| 구분 | 솔루션 |
|---|---|
| 네트워크 보안 | WAF(웹방화벽) · Firewall(네트워크방화벽) · IDS(침입탐지) · IPS(침입방지) · Anti-DDoS(디도스차단) · Anti-APT(APT대응) · Network Forensic(네트워크포렌식) · WIPS(무선침입방지) · NAC(네트워크접근제어) · UTM(통합보안시스템) · VPN(가상사설망) |

!!! tip "구분 포인트"
    IDS(탐지만)와 IPS(탐지+차단)의 차이, EDR과 Anti-Virus의 차이(EDR은 행위기반 탐지+사후대응), HSM과 OTP의 차이(HSM은 암호키를 물리적으로 안전하게 보관하는 하드웨어, OTP는 1회용 인증번호) 등 유사 솔루션 간 차이를 정확히 구분해서 암기하세요.

## 7. 핵심 암기 표 — 시스템 보안

| 주제 | 핵심 키워드 |

| HeartBleed 조치 | 시스템: OpenSSL 업데이트 / 서비스: 인증서 재발급 + 비밀번호 재설정 |

| SOAR vs SIEM | SIEM: 탐지 중심 / SOAR: 탐지+자동 대응 |
| 보안관제 구성요소 | 에이전트 → 정보수집 서버 → 통합관제 서버 |

| UID/GID = 0 위험 | root 외 계정에 0 부여 시 권한탈취 의심 → 정기 점검 |
| shadow minlife/maxlife | 최소 1일(재사용 방지) / 최대 90일(유출 대비) |
| inode MAC Time | Modification(내용)/Access(접근)/Change(속성) |
| 하드링크 vs 심볼릭링크 | 하드=동일 inode 공유(동일 파일시스템만) / 심볼릭=경로를 가리키는 별도 파일 |

| 디지털 포렌식 8분야 | 디스크/휘발성(라이브)/네트워크/이메일/웹/모바일/멀티미디어/DB 포렌식 |
