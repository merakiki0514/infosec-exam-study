# 파트 3. 시스템 보안

시스템 보안은 리눅스/윈도우 보안 설정, 로그 분석, 소프트웨어 취약점을 다룹니다. 실무형 문제에서 직접 명령어와 설정값을 작성해야 하므로 정확한 암기가 필요합니다.

## 1. 리눅스 핵심 보안 설정

> 출제 이유: 리눅스 보안 설정 파일의 경로와 파라미터, 명령어를 정확히 알아야 실무형 문제를 풀 수 있습니다.

### 1-1. 계정 및 패스워드 보안

| 항목 | 파일/설정 |
|---|---|
| 패스워드 최소 길이 설정 (24년도 2회) | 파일: `/etc/login.defs` / 설정: `PASS_MIN_LEN 8` |
| 패스워드 정책 주요 파라미터 | `PASS_MAX_DAYS`: 최대 사용 기간 / `PASS_MIN_DAYS`: 최소 사용 기간 / `PASS_MIN_LEN`: 최소 길이 / `PASS_WARN_AGE`: 만료 경고 일수 |
| /etc/passwd 구조 (26년도 1회) | `username:x:UID:GID:comment:home:shell` / x → 패스워드가 /etc/shadow에 저장됨을 의미 |
| /etc/shadow 구조 (25년도 4회) | `username:$ID$salt$hash:lastchg:min:max:warn:inactive:expire` / $ID: 해시 알고리즘 식별자 ($1=MD5, $5=SHA-256, $6=SHA-512) |
| 암호화 패스워드 파일 (25년도 2회) | `/etc/shadow` — 암호화된 패스워드 저장, root만 읽기 가능 |

### 1-2. 리눅스 핵심 로그 파일 & 명령어

| 명령어/파일 | 설명 |
|---|---|
| utmp (24년도 4회) | 현재 로그인 중인 사용자 정보 (who, w 명령이 참조) |
| wtmp (24년도 4회) | 로그인·로그아웃 이력 전체 기록 (last 명령이 참조) |
| lastlog (24년도 4회) | 각 계정의 마지막 로그인 정보 (lastlog 명령이 참조) |
| lastb (25년도 1회) | 로그인 실패 기록 (/var/log/btmp 파일 참조) |
| lastcomm (25년도 2회) | 실행된 명령어 이력 확인 (process accounting 기반) |
| lsof (25년도 1회) | List Open Files — 시스템의 모든 프로세스가 열어놓은 파일·소켓 정보 확인. 악성 프로세스의 열린 포트 확인에 활용 |
| /var/log/messages | 시스템 전반의 로그. Promiscuous Mode 진입 로그 등 기록 |
| /var/log/secure | 인증·권한 관련 로그 (SSH 접속, su 명령 등) |
| /var/log/syslog | Ubuntu/Debian 계열 시스템 로그 (/var/log/messages 대응) |

!!! important "핵심"
    lastb = 실패 로그인 / lastlog = 마지막 로그인 / wtmp = 전체 이력 / utmp = 현재 — 4가지 구분이 자주 출제됩니다.

### 1-3. 리눅스 보안 실무 설정 (25년도 4회)

| 설정 항목 | 방법 |
|---|---|
| 세션 타임아웃 | `export TMOUT=600` → `/etc/profile` 또는 `/etc/bashrc`에 추가 (600초 = 10분) |
| root 콘솔 접근 제한 | `/etc/securetty` — root가 로그인 가능한 터미널(tty) 목록 관리. 불필요한 항목 제거 |
| 파일 권한 설정 | 644: 일반 설정 파일 (소유자 읽기/쓰기, 그룹/기타 읽기만) / 400: 패스워드·인증 관련 파일 (소유자 읽기만) |
| World-writable 파일 탐지 | `find / -type f -perm -2` (-2 = other에 쓰기 권한 있는 파일) |
| 기본 umask 설정 | `umask 022` → 생성 파일 기본 권한 644, 디렉터리 755 |
| 불필요 서비스 비활성화 | `systemctl disable [서비스명]` 또는 `chkconfig [서비스명] off` |

### 1-4. 쉘(Shell) 정의와 기능 (25년도 1회)

| 항목 | 내용 |
|---|---|
| 정의 | 사용자와 커널(운영체제) 사이에서 명령어를 해석해 주는 대화형 사용자 인터페이스 (명령어 해석기) |
| 종류 | sh, bash (가장 일반적), csh, ksh, zsh 등 |

**쉘의 주요 기능 8가지**

1. 자체 내장 명령어 제공 (cd, echo, export 등)
2. 리다이렉션(Redirection): 표준 입력/출력/오류 방향 재지정 (`>`, `>>`, `<`, `2>`)
3. 파이프라인(Pipeline): 명령어 간 데이터 전달 ( `|` 연산자 )
4. 와일드카드(Wildcard): 파일명 패턴 매칭 (`*`, `?`, `[ ]`)
5. 조건부/무조건부 명령열 작성 (if-else, for, while 등)
6. 서브쉘 생성: 현재 쉘 내에서 하위 쉘 프로세스 생성
7. 백그라운드 프로세스 처리 (`&` 연산자)
8. 쉘 스크립트 작성 및 실행

### 1-5. PATH 환경변수 취약점 (root 홈·패스 디렉터리 권한)

| 항목 | 내용 |
|---|---|
| 취약 원리 | root 계정의 PATH 환경변수에 `.`(현재 디렉터리 지칭)이 포함되어 있으면, root 계정으로 접속한 관리자가 의도하지 않은 현재 디렉터리에 있는 명령어가 실행될 수 있음. `.`이 `/usr/bin`, `/bin`, `/sbin` 등 정상 명령어들이 있는 디렉터리보다 PATH 환경변수에 우선하여 있으면, 현재 디렉터리에 변조된 명령어(예: `ls`)를 악의적으로 삽입해 명령어 입력 시 변조된 명령어가 실행될 수 있음 |
| 점검 파일 | `/etc/profile`(모든 사용자 로그인 시 적용) 또는 root 홈 디렉터리의 `.bash_profile` |
| 취약 설정 예시 | `PATH=.:$PATH` (`.`이 맨 앞 또는 중간에 위치 → 취약) |
| 조치 방법 | PATH 환경변수에서 `.`을 제거하거나, 반드시 필요하다면 PATH 문자열의 **맨 마지막으로 이동** |

!!! tip "시스템에서 명령어를 찾는 절차"
    1. PATH 환경변수에 설정된 경로를 순서대로 탐색하며 명령어를 찾는다.
    2. 명령어가 있으면 실행 권한을 확인한다.
    3. 실행 권한이 있다면 명령어를 실행시킨 사용자 ID(UID)로 명령어를 실행한다.
    4. 실행파일에 setuid/setgid가 설정되어 있다면 소유자/소유그룹 권한으로 명령어를 실행한다.

## 2. 윈도우 보안 설정

> 출제 이유: 윈도우 그룹 계정, UAC, 이벤트 로그 설정이 반복 출제됩니다.

### 2-1. 윈도우 그룹 계정 (24년도 1회)

| 그룹 | 설명 |
|---|---|
| Administrators | 도메인 자원 및 로컬 컴퓨터에 대한 모든 권한을 가진 관리자 그룹 |
| Power Users | 로컬 컴퓨터에서 시스템 관리 능력 보유. 외부 네트워크에서는 일반 사용자 수준 |
| Backup Operators | 시스템 백업 목적으로 모든 파일·디렉터리 접근 가능 (백업용 특수 권한) |
| Users | 도메인과 로컬 컴퓨터를 일반적으로 사용하는 그룹 |
| Guest | 도메인 사용 권한 제한, 시스템 설정 변경 권한 없음 |

### 2-2. UAC (User Account Control) (24년도 2회)

| 항목 | 내용 |
|---|---|
| 정의 | 사용자가 관리자 권한이 필요한 작업을 수행할 때 승인을 요구하는 윈도우 보안 기능 |
| 예(Y) 버튼 비활성화 이유 | 윈도우 Administrator 계정이 비활성화 상태이거나 존재하지 않으면 권한 상승이 불가능하므로 예(Y) 버튼이 비활성화됨 |

### 2-3. 윈도우 이벤트 로그 (25년도 2회)

**최대 이벤트 로그 크기 계산**

- 계산식: 단일 이벤트 최대 크기(500 Byte) × 하루 이벤트 발생량(1,000개) × 보관 기간(30일)
- 계산값: 500 × 1,000 × 30 = 15,000,000 Byte (약 15MB)

**이벤트 로그 크기 설정 경로**: 이벤트 뷰어(`eventvwr.msc`) 실행 → 해당 로그 선택 → 속성 → 일반 → 최대 로그 크기 항목 설정

### 2-5. NetBIOS 취약점 (25년도 1회)

| 항목 | 내용 |
|---|---|
| 취약한 이유 | 인터넷에 직접 연결된 윈도우 시스템에서 NetBIOS와 TCP/IP 바인딩이 활성화되어 있으면, 인터넷을 통해 외부 공격자가 윈도우 공유 자원에 접근할 수 있는 취약점 발생 |
| 조치 방법 | `ncpa.cpl`(네트워크 연결 제어판) 실행 → 네트워크 인터페이스 선택 → TCP/IPv4 속성 → 고급 → WINS 탭 → "NetBIOS over TCP/IP 사용 안 함" 선택 |
| 관련 포트 | TCP/UDP 137(NetBIOS Name Service), 138(Datagram), 139(Session) |

## 3. 주요 보안 취약점

> 출제 이유: 유명 취약점은 CVE 수준에서 개념과 조치 방법을 물어봅니다. 특히 HeartBleed는 조치를 시스템적/서비스적으로 구분하여 서술해야 합니다.

### 3-1. HeartBleed (하트블리드) (24년도 2회)

| 항목 | 내용 |
|---|---|
| CVE | CVE-2014-0160 |
| 영향 대상 | OpenSSL 1.0.1 ~ 1.0.1f (TLS Heartbeat 확장 구현 취약점) |
| 원리 | TLS Heartbeat 요청에 포함된 메시지 길이를 검증하지 않아, 서버 메모리에서 최대 64KB의 데이터를 읽어내는 메모리 과다 읽기(Buffer Over-Read) 취약점 |
| 유출 정보 | 서버의 SSL 개인키, 사용자 세션 토큰, 패스워드 등 메모리 내 민감 정보 |

**조치 방법**

| 조치 구분 | 내용 |
|---|---|
| 시스템적 조치 | 취약한 OpenSSL 라이브러리를 취약점이 패치된 버전(1.0.1g 이상)으로 업데이트 |
| 서비스적 조치 1 | 서버 SSL/TLS 개인키가 유출되었을 가능성이 있으므로 인증서 재발급 검토 |
| 서비스적 조치 2 | 조치 완료 후 사용자들의 비밀번호 재생성 유도 → 탈취된 계정을 통한 추가 피해 방지 |

### 3-2. 버퍼 오버플로우 (Buffer Overflow) (25년도 2회)

| 항목 | 내용 |
|---|---|
| 정의 | 연속된 메모리 공간을 사용하는 프로그램에서 할당된 메모리의 범위를 넘어선 위치에 자료를 읽거나 쓰려고 할 때 발생. 프로그램의 오작동을 유발시키거나, 악의적인 코드를 실행시킴으로써 공격자가 프로그램을 통제할 수 있는 권한을 획득하게 됨 |
| 스택(Stack) 버퍼 오버플로우 | 스택은 함수 처리를 위해 지역변수 및 매개변수가 위치하는 메모리 영역. 스택에 할당된 버퍼들이 문자열 처리 등에 의해 정의된 버퍼의 한계치를 넘는 경우, 버퍼 오버플로우가 발생하여 복귀 주소(Return Address)를 변경하고 공격자가 원하는 임의의 코드를 실행 |
| 힙(Heap) 버퍼 오버플로우 | 힙은 사용자가 동적으로 할당하는 메모리 영역(`malloc()` 등 메모리 할당 함수 이용). 힙에 할당된 버퍼들에 문자열 등이 저장될 때, 최초 정의된 힙의 메모리 사이즈를 초과하여 문자열 등이 저장되는 경우 버퍼 오버플로우가 발생하여 데이터와 함수 주소 등을 변경하여 공격자가 원하는 임의의 코드를 실행 |
| 위험 함수 (취약) | `strcpy(char *dst, const char *src)`: src 문자열의 길이를 체크하지 않으므로 dst 버퍼를 초과하는(오버플로우) 결과 발생 가능. 그 외 `strcat()`, `gets()`, `sprintf()`, `scanf()` — 길이 검사 없음 |
| 안전한 대안 함수 | `strncpy(char *dst, const char *src, size_t len)`: src 문자열의 len 만큼을 dst 버퍼에 저장 — 길이를 제한하므로 오버플로우에 안전. 그 외 `strncat()`, `fgets()`, `snprintf()` |
| C언어 문자열 처리 | C언어에서 문자열은 null 문자(`0x00`)로 문자열의 끝을 표현. 예: "ABCD"(4글자)는 실제로 "ABCD\0"의 5개 문자로 저장됨 → 버퍼 크기를 계산할 때 null 문자 자리를 빠뜨리면 오프바이원(off-by-one) 오버플로우가 발생할 수 있음 |

**버퍼 오버플로우 방어 기법**

- 스택 카나리(Stack Canary): 리턴 주소 전에 랜덤 값을 배치하여 덮어쓰기 감지
- ASLR (Address Space Layout Randomization): 메모리 주소를 무작위 배치하여 공격 어렵게 함
- NX/DEP (No-Execute / Data Execution Prevention): 스택·힙 영역에서 코드 실행 불가
- 안전한 라이브러리 함수 사용

### 3-3. APT & 사이버 킬 체인

| 항목 | 내용 |
|---|---|
| APT 정의 (24년도 2회) | 특정 대상을 목표로 다양한 공격 기법을 동원하여 장기간 지속적으로 침투하고 정보를 탈취하는 고도화된 위협 |
| APT 특징 | 고도화된 기법 / 장기간 은밀한 공격 / 특정 대상 표적화 / 다단계 공격 |
| 사이버 킬 체인 (25년도 1회) | APT 공격 대응 프레임워크 (Lockheed Martin 제안). 7단계로 공격 과정 모델링 |

**사이버 킬 체인 7단계**

1. 정찰(Reconnaissance): 목표 대상 정보 수집
2. 무기화(Weaponization): 취약점 악용 코드·페이로드 제작
3. 전달(Delivery): 이메일 첨부, 악성 URL 등을 통해 페이로드 전달
4. 익스플로잇(Exploitation): 취약점 실행으로 침투
5. 설치(Installation): 백도어·RAT 설치
6. 명령·제어(C2, Command & Control): C2 서버와 통신으로 원격 제어
7. 목표 달성(Actions on Objectives): 데이터 유출, 서비스 방해 등 최종 목표 수행

### 3-4. 제로데이(Zero-Day) 취약점 (25년도 4회)

| 항목 | 내용 |
|---|---|

### 3-5. 퍼징(Fuzzing) (26년도 1회, 24년도 1회)

## 5. 접근통제 모델 (필수 암기)

> 출제 이유: 매 회차 출제되는 핵심 이론입니다. 3가지 모델의 차이를 명확히 설명할 수 있어야 합니다.

### 5-1. 접근통제 3가지 모델 (24년도 4회)

| 모델 | 정의 / 특징 |
|---|---|
| DAC (임의적 접근통제) / Discretionary Access Control | 주체 또는 그들이 속한 그룹의 ID에 근거하여 객체 접근 제한 / 자원 소유자가 접근 권한을 임의로 설정 가능 / 유연하지만 권한 관리가 분산되어 통제 어려움 / 예: 리눅스 파일 권한 (chmod), ACL |
| MAC (강제적 접근통제) / Mandatory Access Control | 객체의 비밀성 등급과 주체의 허가 등급(보안 레이블)에 근거하여 접근 강제 제한 / 중앙에서 관리자가 정책 설정, 소유자도 임의 변경 불가 / 군사·정부 기관에 적합 / 예: SELinux |
| RBAC (역할 기반 접근통제) / Role-Based Access Control | 사용자의 역할(Role)에 따라 접근 권한 부여 / 역할 변경 시 자동으로 권한 변경, 대규모 조직에서 관리 효율 높음 / 예: ERP 시스템의 부서별 권한 |

!!! important "핵심"
    DAC=소유자 자유 설정, MAC=보안 등급 강제, RBAC=역할별 권한 — 이 3가지 핵심 차이를 한 문장씩 서술할 수 있어야 합니다.

### 5-2. 추가 접근통제 모델

| 모델 | 설명 |
|---|---|
| ABAC (속성 기반 접근통제) | 사용자·자원·환경의 다양한 속성(시간, 위치, 부서 등)을 조합하여 접근 제어. 가장 세밀한 제어 가능 |
| Bell-LaPadula 모델 | 기밀성 중심 MAC 모델. No Read Up(상위 등급 읽기 금지), No Write Down(하위 등급 쓰기 금지) |
| Biba 모델 | 무결성 중심 MAC 모델. No Write Up(상위 등급 쓰기 금지), No Read Down(하위 등급 읽기 금지) |

## 6. 보안 관제 솔루션

### 6-1. SOAR (24년도 1회)

| 항목 | 내용 |
|---|---|
| 정의 | Security Orchestration, Automation and Response. 보안 운영의 자동화·오케스트레이션·대응을 통합하는 플랫폼 |
| 특징 | SIEM보다 진보된 형태. AI/빅데이터 기반 지능형 공격 탐지 및 자동 대응 |
| SIEM과의 차이 | SIEM: 로그 수집·분석·탐지 중심 / SOAR: 탐지 + 자동화된 대응(Playbook) 수행 |

### 6-2. SIEM (26년도 1회)

| 항목 | 내용 |
|---|---|
| 정의 | Security Information and Event Management. 다양한 보안 장비·서버의 로그와 이벤트를 실시간으로 수집·상관 분석하여 보안 위협을 통합 관제하는 시스템 |
| 기능 | 로그 통합 수집 / 실시간 모니터링 / 상관 분석(Correlation) / 경보 / 보고서 생성 |
| 대표 제품 | IBM QRadar, Splunk, ArcSight, LogRhythm 등 |

### 6-3. 보안 관제 구성요소 3가지 (25년도 2회)

| 구성요소 | 역할 |
|---|---|
| 에이전트 (Agent) | 보안 장비·서버·네트워크 장비에 설치. 해당 시스템의 로그 정보를 실시간으로 중앙관제센터에 전송 |
| 정보수집 서버 (Information Collection Server) | 에이전트에서 전송된 대량의 정보를 수집·처리하여 DB에 저장 |
| 통합관제용 서버 (SMS, Security Monitoring System) | 이벤트 로그 종합 분석. 다양한 정보를 상관 분석하여 관제 담당자 지원 및 경보 발령 |

## 7. 핵심 암기 표 — 시스템 보안

| 보안관제 구성요소 | 에이전트 → 정보수집 서버 → 통합관제 서버 |
