# 파트 8. 침해사고 분석 및 대응

이 파트는 실기 시험에서 자주 빠뜨리기 쉬운 영역입니다. IDS/IPS·보안솔루션의 실제 운영, 취약점 점검 도구의 용도, 침해사고 발생 시 시나리오별 분석 절차를 다룹니다. Snort 룰 문법과 iptables 심화 옵션, 침해사고 유형별 시나리오는 실무형 문제로 자주 출제됩니다.

## 1. 침입탐지시스템(Snort) 심화

### 1-1. Snort 개요

1998년 마틴 로시(Martin Roesch)가 개발한 오픈소스 네트워크 IDS/IPS로, "Sniffer and More"에서 유래된 이름이다. 크게 3가지 기능을 수행한다.

| 기능 | 설명 |
|---|---|
| 패킷 스니퍼(Sniffer) | 네트워크상의 패킷을 스니핑하여 보여주는 기능 |
| 패킷 로거(Logger) | 모니터링한 패킷을 저장하고 로그에 남기는 기능 |
| 네트워크 IDS/IPS | 네트워크 트래픽을 분석하여 공격을 탐지·차단하는 기능 |

### 1-2. Snort 룰(Rule) 구조

룰은 크게 **헤더(Header)** 부분과 **바디(Body)** 부분으로 구성된다. 헤더는 처리방식·프로토콜·IP주소·포트번호 등 "처리할 패킷을 판단하는 기준"을, 바디는 "패킷을 탐지하기 위한 규칙"을 명시한다.

```
alert tcp any any -> 192.168.1.10 80 (msg:"SQL Injection Attempt"; content:"UNION SELECT"; sid:1000001; rev:1;)
└──┬──┘ └┬┘ └┬─┘└┬┘  └────┬─────┘ └┬┘         └──────────────── 바디(옵션) ────────────────┘
 Rule Action 프로토콜  출발지  목적지          방향
```

| 헤더 구성요소 | 설명 |
|---|---|
| Rule Actions | 패킷이 룰에 매칭되었을 때의 처리방식. alert(경보+로깅), log(로깅만), pass(무시), drop(차단+로깅, IPS 모드), reject(차단+응답) 등 8가지 유형 |
| Protocols | 탐지할 프로토콜. TCP, UDP, ICMP, IP 4가지 지원 |
| IP Addresses | 출발지/목적지 IP. 단일 IP, CIDR 대역, IP 리스트(`[192.168.159.10,192.168.159.20]`) 지정 가능. `any`는 전체, `!`(negation operator)로 특정 IP 제외 가능(예: `!192.168.159.10`) |
| Port Numbers | 출발지/목적지 포트. 단일 포트, 포트 범위(`1:1023`=1~1023, `:1024`=1024 이하, `1024:`=1024 이상), 포트 리스트 지정 가능 |

!!! important "핵심"
    Snort 룰이 지나치게 광범위하면 오탐(False Positive) 증가, 지나치게 좁으면 미탐(False Negative) 증가, 지나치게 복잡하면 처리 부하 증가 — 이 3가지 트레이드오프는 [25년도 4회 기출](../past-exams/2025-4.md)에서 이미 출제된 서술형 포인트입니다.

## 2. 침입차단시스템(iptables) 심화

### 2-1. NTP DDoS 탐지·차단 실무 (monlist 점검)

**취약 여부 점검**: monlist 질의로 확인한다.

```bash
ntpdc -n -c monlist <점검 대상 NTP 서버>
# -n : 응답 결과의 호스트 주소를 숫자 형식으로 출력
# -c : 질의할 명령어(monlist) 지정
```

**보안장비(iptables)를 통한 차단**: 일반적인 NTP 응답 패킷은 100byte 이하(48byte)이지만, monlist 질의에 대한 응답은 400byte 내외로 발생하므로 **패킷 크기를 기준으로 차단**한다.

```bash
iptables -A OUTPUT -p udp --sport 123 -m length --length 100:65535 -j DROP
# -A OUTPUT : 응답 패킷이므로 OUTPUT 체인에 설정
# -p udp --sport 123 : NTP는 UDP 프로토콜, 응답 패킷의 출발지 포트 123
# -m length --length 100: : length 모듈로 100byte 이상인 패킷을 매칭
```

**iptables length 모듈(`-m length`) 사용법**

| 옵션 | 의미 |
|---|---|
| `--length 1000` | 패킷 크기가 정확히 1000byte인 패킷 |
| `--length 1000:` | 패킷 크기가 1000byte 이상인 패킷 |
| `--length 1000:2000` | 패킷 크기가 1000byte 이상 2000byte 이하인 패킷 |
| `--length :2000` | 패킷 크기가 2000byte 이하인 패킷 |

## 3. 보안 솔루션 종류 및 특징 비교

| 솔루션 | 위치/동작 | 핵심 기능 |
|---|---|---|
| 방화벽(Firewall) | 네트워크 경계 | IP/포트 기반 접근 제어 (3~4계층) |
| IDS | 네트워크/호스트, 인라인 아님(탐지만) | 공격 탐지·경보. 트래픽 차단 불가 |
| IPS | 네트워크, 인라인(트래픽 경로 상) | 공격 탐지 즉시 차단까지 수행 |
| WAF | 웹 서버 앞단, 7계층 | SQL Injection, XSS 등 웹 공격 패턴 차단 |
| DLP | 엔드포인트/네트워크 | 중요 데이터 외부 유출 탐지·차단 ([법·제도 파트](06-law-practice.md) 참고) |

### 3-1. 물리적 네트워크 보안장비 구성 (배치 순서)

일반적인 기업 네트워크의 보안장비는 다음 순서로 배치됩니다(인터넷 → 내부망 방향).

**인터넷 구간 → Anti-DDoS → 방화벽(1차) → DMZ 구간(IDS·Network Forensic·Anti-APT, IPS 1차, WAF) → 방화벽(2차) → IPS(2차) → 내부망**

| 장비 | 배치 위치 | 역할 |
|---|---|---|
| Anti-DDoS(디도스 차단 시스템) | 네트워크 구성상 가장 상단 | 디도스 공격(특히 Flooding 계열)으로부터 다른 장비들을 보호 |
| 방화벽(Firewall) | 서로 다른 보안 레벨의 네트워크 경로 사이(인터넷-DMZ 사이, DMZ-내부망 사이 등) | 출발지/목적지 IP·Port·프로토콜 기반 패킷 필터링. 일반적으로 고가용성(HA) 확보를 위해 Active-Standby 또는 Active-Active 이중화 구성 |
| 상태 검사(Stateful Inspection) | 방화벽 내부 기능 | 단순 IP/Port 필터링이 아니라 일정 시간 프로토콜별 연결 상태 정보까지 검사하는 기능. 이스라엘 보안업체 **체크포인트(Checkpoint)사가 최초 개발**(1990년대 초) |
| DMZ(비무장지대) 구간 | 인터넷과 내부망 사이의 완충 구간 | 외부에 공개해야 하는 서버(WEB·DNS·Mail 서버 등)를 배치하여, 침해당하더라도 내부망 직접 접근을 차단 |

### 3-2. 보안 솔루션(장비) 자체의 계정 관리 취약점

| 항목 | 내용 |
|---|---|
| default 계정 변경 | 보안장비의 기본 관리자 계정(제조사 출고 시 기본 설정된 계정)은 인터넷·매뉴얼 등에 공개되어 있으므로, 변경하지 않으면 공격자가 이를 이용해 보안장비를 장악하고 설정값을 변경해 무력화할 수 있음 → **default 계정을 반드시 변경**(변경 불가 시 기본 패스워드 변경으로 보완) |
| default 패스워드 변경 | 기본 관리자 계정의 패스워드도 공개되어 있으므로 반드시 변경. 특수문자·숫자·영문 대소문자를 포함하여 **8자리 이상**으로 설정 |
| 계정별 권한 설정 | 등록된 계정에 용도별 권한을 부여하여, 권한 없는 사용자의 설정 변경으로 인한 시스템 침입 경로 차단. 관리자 계정이 아닌 일반 계정이 탈취되었을 때 보안장비 전체가 장악되지 않도록 함 |

!!! tip "핵심"
    "보안장비 자체도 하나의 시스템"이라는 관점에서, 일반 서버·시스템 계정 보안(기본 계정·패스워드 변경, 최소 권한)과 동일한 원칙이 적용된다는 것이 이 절의 핵심입니다.

## 4. 시스템 점검 도구

> 출제 이유: "시험에 자주 출제되는 점검 도구 위주로 정리한 내용입니다. 각 도구의 명칭과 기능을 기억해야 합니다"(교재 강조) — 특히 무결성 및 루트킷 탐지도구는 동작 원리와 점검 결과에 대해 분석할 수 있도록 충분히 학습이 필요합니다.

| 도구 | 용도 | 특징 |
|---|---|---|
| Nessus | 취약점(Vulnerability) 점검 | 미국 테너블(Tenable)사가 개발·배포. 로컬 또는 원격지에서 시스템·네트워크·웹 애플리케이션 취약점을 점검하고, 취약점 내용과 해결 방법을 상세히 제공. 클라이언트/서버 구조로 동작하며 TXT·HTML·PDF 등 다양한 포맷으로 리포트 |
| Nikto | 웹 서버 취약점 점검 | 공개용 웹 취약점 점검 도구. 웹서버 설치 시 기본적으로 설치되는 위험한 파일·CGI, 웹서버의 종류·버전 등을 스캔. 방대한 DB를 이용해 취약한 CGI 파일을 스캔하는 기능이 뛰어남 |
| Tripwire | 무결성(Integrity) 점검 | 파일의 해시값(체크섬)을 DB에 저장해두고, 이후 변경 여부를 비교해 무결성 훼손 탐지 |
| chkrootkit | 루트킷(Rootkit) 점검 | 시스템에 설치된 루트킷의 흔적(숨겨진 프로세스·파일·백도어)을 탐지하는 오픈소스 도구 |

!!! important "핵심"
    "취약점 점검=Nessus(시스템·네트워크 전반)/Nikto(웹 특화)", "무결성 점검=Tripwire", "루트킷 점검=chkrootkit" — 도구와 용도를 1:1로 암기하세요. [26년도 1회 기출](../past-exams/2026-1.md)에서 무결성 점검 도구와 Nessus를 묻는 문제가 출제되었습니다.

## 5. 침해사고 유형별 시나리오

> 교재 강조: "최근 서술형 및 실무형 문제들은 복잡적인 시나리오 형식으로 공격자 관점 혹은 분석자 관점에서 행위를 보여주고 있습니다. 이런 문제에 대응하기 위해서는 전체적인 시나리오를 먼저 이해하고 행위를 구체적으로 분석할 수 있어야 합니다."

### 5-1. 리버스 쉘(Reverse Shell) 침해사고

**전형적 시나리오**: 방화벽 정책상 외부(Inbound)에서는 80/tcp(HTTP)만 허용, 그 외 인바운드는 차단(DROP)되어 있지만 내부에서 외부로 나가는 아웃바운드(Outbound)는 전체 허용(ACCEPT)되어 있는 환경.

1. 공격자는 웹서버 Telnet 서비스에 무작위 대입(Brute Force)/사전(Dictionary) 공격을 수행해 루트(root) 계정 패스워드를 탈취한다 (외부에서 직접 Telnet 접근은 방화벽에 막혀 있으므로, 먼저 다른 경로로 내부에 침입한 뒤 시도).
2. 공격자는 반복적 침입을 손쉽게 하기 위해 일반 사용자 계정처럼 보이는 루트 권한 사용자 계정(UID=0, GID=0)을 생성한다.
3. 공격자는 외부에서 웹서버에 지속적으로 접근할 수 있도록 **netcat 프로그램을 이용한 리버스 쉘(Reverse Shell) 연결 작업을 `/etc/crontab`(cron 테이블)에 등록**한다.
4. 공격자는 외부에서 주기적으로 리버스 쉘을 연결하여 웹서버에 악의적인 명령을 수행한다.

| 항목 | 내용 |
|---|---|
| 핵심 원리 | 인바운드는 엄격히 통제해도 아웃바운드는 느슨한 방화벽 정책의 비대칭을 악용 |
| 탐지 포인트 | UID/GID가 0인 의심스러운 신규 계정, `/etc/crontab`의 비정상 등록 작업, 평소 없던 외부 아웃바운드 연결 |
| 대응 | 아웃바운드 트래픽도 화이트리스트 기반으로 통제, 계정·크론탭 변경 모니터링 |

### 5-2. 루트킷(Rootkit) 침해사고

**전형적 시나리오**: 공격자가 Tomcat 웹서버 취약점 스캔을 통해 관리자 페이지(`/manager/html`)가 외부에 노출되어 있고, 초기 설정 계정(id:tomcat, password:tomcat)을 그대로 사용 중임을 확인.

1. 공격자는 Tomcat 웹서버 관리자 페이지 취약점(예: CVE-2009-3843)을 익스플로잇(Exploit)하여 쉘 코드(Shell Code)를 실행, 리버스 쉘(Reverse Shell)을 연결한다.
2. 공격자는 리버스 쉘을 이용해 공격 행위 은닉을 위한 **루트킷(Rootkit)**을 웹서버에 설치한다.
3. 지속성 확보를 위해 netcat 프로그램을 이용한 리버스 쉘 연결 작업을 cron 테이블에 등록한다.
4. 공격자는 외부에서 주기적으로 리버스 쉘을 연결하여 악의적인 명령을 수행한다.

**관련 지식: 익스플로잇(Exploit)과 쉘 코드(Shell Code)**

- **익스플로잇**: 소프트웨어나 하드웨어의 버그 또는 취약점을 이용해 공격자가 의도한 동작이나 명령을 실행하도록 하는 코드(또는 그러한 행위)
- **쉘 코드**: 익스플로잇에 성공하면 프로그램 실행 제어권을 획득하게 되며, 공격자가 의도한 명령을 담고 있는 코드를 쉘 코드라 함

| 항목 | 내용 |
|---|---|
| 탐지 | 신뢰할 수 있는 외부 매체로 부팅 후 점검, chkrootkit 등 전용 도구 사용, Tripwire로 시스템 명령어(ls, ps, netstat 등) 변조 여부 확인 |
| 대응 | 관리자 페이지 외부 노출 차단, 초기 설정 계정(기본 아이디/패스워드) 변경, 루트킷 발견 시 해당 시스템은 재설치를 원칙으로 함 |

### 5-3. DBD (Drive By Download) 침해사고

**전형적 시나리오**: 공격자가 악성코드 경유지로 사용할 정상 사이트(A)와 최종 유포지로 쓸 사이트(C)를 모두 해킹해 악성 스크립트를 심어놓은 상태.

1. 희생자(사용자)는 평소 자주 방문하는 **경유지(A)** 사이트의 정상 페이지를 아무 의심 없이 방문한다.
2. A 사이트의 정상 응답 페이지에는 숨겨진 `<iframe>` 태그를 통해 **중계지(B)** 사이트로 리다이렉트하는 난독화된 악성 스크립트가 삽입되어 있다.
3. 사용자 브라우저는 중계지(B)의 응답 페이지에 숨겨진 iframe 태그를 통해 최종 **유포지(C)** 사이트로 리다이렉트된다.
4. 유포지(C)는 사용자 브라우저(취약한 플러그인·버전)를 겨냥한 **익스플로잇 코드와 쉘 코드(악성코드)**가 삽입된 응답 페이지를 반환한다.
5. 사용자 브라우저에서 익스플로잇이 성공하면 악성코드가 설치·동작한다.

| 항목 | 내용 |
|---|---|
| 핵심 구조 | 경유지 → 중계지 → 유포지 다단계 리다이렉트(iframe 난독화 스크립트) |
| 정의 | 사용자가 악성 웹사이트를 방문하는 것만으로(클릭 등 추가 행위 없이) 브라우저·플러그인 취약점을 통해 자동으로 악성코드가 다운로드·설치되는 공격 |
| 대응 | 브라우저·플러그인 최신 버전 유지, 웹 필터링 솔루션 적용, 정상 사이트의 웹 취약점(해킹 경유지화 방지)을 사전 점검 |

### 5-4. 워터링 홀(Watering Hole) 침해사고

**전형적 시나리오** (Target = 특정 임직원, Mission = 임직원 정보 탈취 및 시스템 파괴):

1. 공격자는 알기사 사이트 임직원 정보 탈취 및 시스템 파괴를 목적으로, 관리자가 업무용 PC로 자주 방문하는 쇼핑몰 사이트를 사전에 조사한다.
2. 공격자는 해당 쇼핑몰 사이트를 해킹하여, 관리자가 접속 시 악성코드 유포지로 리다이렉트하는 스크립트를 삽입한다.
3. 관리자는 평소처럼 쇼핑몰에 접속했다가 자신도 모르게 유포지로 리다이렉트되어 악성코드에 감염된다.
4. 공격자는 감염된 PC에 연결된 백도어(리버스 쉘)를 이용해 포트 스캐너, SSH 클라이언트, 키로거 등 추가 공격 도구를 다운로드한다.
5. 공격자는 내부 시스템·네트워크 정보를 수집하고 키로거로 내부 그룹웨어 서버의 관리자 계정 정보를 알아낸다.
6. 공격자는 SSH 원격 포트 포워딩(Remote Port Forwarding)을 이용해 방화벽을 우회하여 내부 그룹웨어에 접속한다.
7. 공격자는 지속적인 침투를 위해 악성코드(백도어)를 시작 프로그램에 등록한다.
8. 공격자는 SSH 터널링을 통해 내부 그룹웨어에 관리자 권한으로 접속, 임직원 정보를 탈취하고 최종적으로 관리자 PC를 포함한 직원 PC에 디스크 파괴형 악성코드를 유포해 시스템 장애를 유발한다.

| 항목 | 내용 |
|---|---|
| 정의 | 공격 대상이 자주 방문하는 신뢰된 웹사이트를 미리 해킹해 악성코드를 심어두고, 대상이 방문할 때 감염시키는 표적형 공격 기법. APT 공격의 초기 침투 단계로 자주 사용 |
| DBD와의 관계 | 워터링홀은 "누구를 감염시킬 것인가"(표적 선정 전략), DBD는 "어떻게 감염시킬 것인가"(감염 기술) — 워터링홀은 보통 DBD 기법을 통해 실제 감염을 수행 |
| 대응 | 웹 필터링, 방화벽 아웃바운드 정책 강화(SSH 등 불필요한 외부 터널링 차단), 위협 인텔리전스 기반 악성 사이트 차단 |

### 5-5. 악성코드 행위 분석

| 분석 방식 | 설명 |
|---|---|
| 정적 분석 (Static Analysis) | 파일을 실행하지 않고 코드·구조를 분석. 해시값 대조, 문자열 추출, 디스어셈블 |
| 동적 분석 (Dynamic Analysis) | 격리된 샌드박스 환경에서 실제 실행하여 행위(파일 생성, 레지스트리 변경, 네트워크 통신)를 관찰 |

!!! warning "주의"
    악성코드 분석은 반드시 네트워크와 격리된 샌드박스·가상환경에서 수행해야 합니다. 실제 운영망에서 직접 실행하면 2차 감염이 발생할 수 있습니다.

## 6. 주요 취약점 (CVE 사례)

### 6-1. GNU Bash 취약점(ShellShock)

| 항목 | 내용 |
|---|---|
| 발견 | 2014년 9월 스테판 챠젤라스(Stephane Chazelas)에 의해 최초 발견 |
| CVE | CVE-2014-6271 (GNU Bash 원격 명령 실행 취약점) |
| 명칭 유래 | OpenSSL 하트블리드(HeartBleed) 취약점 이후 취약점에 이름을 짓는 유행에 따라 "쉘쇼크(ShellShock)"로 명명 |
| 심각도 | 인터넷을 통해 간단한 명령만으로 시스템을 장악할 수 있는 심각성 때문에 미국 NIST에서는 쉘쇼크의 취약점 등급(CVSS)을 하트블리드 취약점(5점)보다 높은 **최고 점수인 10점**으로 산정·발표 (2014년 4월) |
| 원리 | Bash가 환경변수 값에 포함된 함수 정의 뒤에 이어지는 명령어까지 실행해버리는 취약점. CGI 스크립트 등 외부 입력이 환경변수로 전달되는 경로를 통해 원격 코드 실행 가능 |
| 대응 | 취약하지 않은 Bash 버전으로 업데이트, 불필요한 CGI 스크립트 비활성화 |

### 6-2. NTP / SSDP 분산 서비스 거부(DDoS) 취약점

| 취약점 | 설명 |
|---|---|
| NTP DDoS | monlist 명령을 악용한 반사·증폭 DDoS. 점검·차단 실무는 [본문 2절](#2-1-ntp-ddos-탐지차단-실무-monlist-점검) 참고. [네트워크 보안 파트](01-network.md)에도 대응 방안 정리 |
| SSDP DDoS | SSDP(Simple Service Discovery Protocol)는 네트워크상의 서비스·정보를 검색하는 프로토콜로 프린터·스캐너·IP카메라 등 IoT 기기의 네트워크 탐색 용도로 사용되며 **UDP 1900번 포트**를 사용. 장비 검색 시 **멀티캐스트 주소(239.255.255.250)**로 `M-SEARCH * HTTP/1.1` 요청 패킷을 전송하면, 각 기기가 자신의 서비스 정보를 담아 응답한다. 요청 패킷보다 응답 패킷이 훨씬 크기 때문에(증폭), 출발지를 피해자로 위조하면 반사·증폭 DDoS 공격에 악용된다 |
| SSDP 대응 | 불필요한 UPnP 기능 비활성화, 경계 라우터에서 외부발 1900/UDP 응답 차단 |

## 7. 핵심 암기 표 — 침해사고 분석·대응

| 주제 | 핵심 키워드 |
|---|---|
| Snort 룰 구성 | 헤더(Rule Action+프로토콜+IP+포트) + 바디(msg, content, sid 등 옵션) |
| Snort Rule Actions | alert/log/pass/drop/reject 등 8가지, drop=IPS 모드 차단 |

| Nessus / Nikto | 취약점 점검(시스템·네트워크 전반 / 웹 특화, CGI 스캔) |
| Tripwire | 파일 무결성 점검(해시 비교) |
| chkrootkit | 루트킷 탐지 |
| 리버스 쉘 시나리오 | 아웃바운드 허용 악용, UID/GID=0 계정 생성, crontab에 netcat 등록 |
| 루트킷 시나리오 | 관리자페이지 노출+기본계정 → 익스플로잇 → 루트킷 설치 → 재설치 원칙 |
| DBD 구조 | 경유지 → 중계지 → 유포지, iframe 난독화 리다이렉트 |
| 워터링홀 | 표적이 자주 가는 사이트 감염 → SSH 포트포워딩으로 내부 침투 |
| 악성코드 분석 | 정적분석(코드) vs 동적분석(샌드박스 실행) |
| ShellShock | CVE-2014-6271, CVSS 10점(하트블리드 5점보다 높음), Bash 환경변수 취약점 |
| SSDP DDoS | UDP 1900, 멀티캐스트 239.255.255.250, M-SEARCH 요청/응답 크기 차이로 증폭 |
| 보안장비 배치 순서 | 인터넷→Anti-DDoS→방화벽(1차)→DMZ(IDS/IPS 1차/WAF)→방화벽(2차)→IPS(2차)→내부망 |
| Stateful Inspection | 연결 상태까지 검사하는 방화벽 기능, 체크포인트사 최초 개발 |
| 보안장비 계정 취약점 | default 계정/패스워드 변경 필수 + 계정별 권한 설정(최소 권한) |
