## 14. XSS 공격 2가지

1. **Stored XSS(저장형 XSS)**: 취약한 웹 사이트에 악성 스크립트를 DB 등에 저장해 놓으면(예: 회원정보 변경, 게시판, 댓글, 자료실 등을 이용) 희생자가 해당 자료를 요청했을 때 응답에 해당 악성 스크립트가 삽입되어 클라이언트 측에서 동작하는 공격 기법
2. **Reflected XSS(반사형 XSS)**: 외부에 있는 악성 스크립트(예: 악성 스크립트가 포함된 URL 링크 등)가 희생자의 액션(예: 링크 클릭 등)에 의해 취약한 웹 사이트에 전달되고 응답에 해당 악성 스크립트가 삽입되어 클라이언트 측에서 동작하는 공격 기법

## 15. 생체인식정보 보호 6가지 원칙

1. **비례성**: 생체인식정보 처리에 따른 편익에 비해 개인정보 침해 위험성이 크지 않은지를 고려하여 생체인식정보의 활용여부를 판단
2. **적법성**: 생체인식정보의 수집/이용/제공 등 생체정보 처리의 근거는 적법/명확해야 한다
3. **목적제한**: 생체인식정보를 정보주체에게 동의를 받은 인증/식별 이외의 목적으로 무단으로 활용해서는 안된다
4. **투명성**: 생체인식정보 보호에 관한 사항을 정보주체에게 알기 쉽게 공개한다
5. **안전성**: 생체인식정보가 분실/도난/유출/위조/변조 또는 훼손되지 않도록 안전하게 처리하고 관리한다
6. **통제권보장**: 정보주체가 자신의 생체인식정보를 스스로 통제할 수 있는 수단을 제공한다

## 16. SSL/TLS에서 비대칭키/대칭키 암호의 사용 단계와 용도

**(A) 비대칭키(공개키) 암호 방식**

1. 서버 인증(Server Certificate) 단계: 서버가 전달한 인증서를 클라이언트가 인증기관(CA)의 공개키로 검증하여 서버 인증(서버 신원확인)을 수행하는 데 사용
2. 키 교환(Server Key Exchange, Client Key Exchange) 단계: 다양한 키(세션키, 비밀키, IV 등) 생성에 필요한 마스터 비밀(Premaster Secret)을 생성 및 공유하기 위해 사용
   - RSA 방식: 클라이언트는 사전 마스터 비밀 생성 후 수신한 서버 인증서에 포함된 서버 공개키로 암호화하여 서버에 전달
   - Diffie-Hellman 방식: 서버와 클라이언트는 각각 DH 공개값(공개 매개변수, 공개키)을 교환한 후, 자신의 개인키와 상대방의 공개키를 이용하여 각자 사전 마스터 비밀을 계산

**(B) 대칭키 암호 방식**

1. 암호화 통신 단계(Change Cipher Spec 이후 단계): 핸드셰이크(협상) 과정에서 생성된 세션키와 초기화 벡터(IV)를 사용하여 송수신 메시지를 암호화하기 위해 사용

## 17 (실무형). 웹 프록시(피들러) 분석

**(그림 1) https 복호화 실패 이미지**

1. 오류가 발생한 이유: 피들러 프록시의 루트 CA 인증서가 브라우저/OS의 신뢰된 인증서 저장소에 설치되지 않아 SSL 인증서 검증 실패
2. 해결 방안: 피들러 CA 인증서를 브라우저/OS 신뢰된 루트 인증서로 설치

**(그림 2) 웹페이지 html 코드, title 태그에 alert 스크립트 삽입**

1. 점검 중인 취약점: XSS (Cross-Site Scripting)
2. 대응 방안: HTML 출력 전 사용자 입력값을 HTML 엔티티로 인코딩 (예: `<` → `&lt;`, `>` → `&gt;`, `&` → `&amp;`, `"` → `&quot;`)

## 18 (실무형). CSRF 취약점을 제거한 안전한 코드 분석

**주어진 코드**

```java
// 게시판 글쓰기 페이지 요청을 처리
@RequestMapping("/write.do")
public String boardWrite(@ModelAttribute("BoardModel") BoardModel boardModel, HttpSession session) {
    // 난수 형태의 토큰을 생성하여 세션에 저장
    session.setAttribute("SESSION_CSRF_TOKEN", UUID.randomUUID().toString());
    return "/board/write";
}
// 생성한 토큰을 작업(입력) 페이지에 히든 필드의 값으로 전달
```

**1) 세션과 쿠키에 대해 서술**

- Cookie: 개별 클라이언트의 상태 정보를 클라이언트에 저장하고 HTTP 요청/응답 헤더에 담아서 전달하는 기술로, 클라이언트 해킹이나 스니핑 공격에 의한 정보 노출이나 변조에 취약한 특성이 있음
- Session: 개별 클라이언트의 상태 정보를 서버에 저장하는 기술로, 쿠키 방식에 비해 안전하게 상태 정보를 유지할 수 있음

**2) 보기의 코드에서 알 수 있는 취약점과 이를 이용한 공격 기법**

→ CSRF 토큰을 이용하여 CSRF 취약점을 제거한 예시

- **취약점**: CSRF 취약점
- **공격 기법**: 웹 애플리케이션에서 정상적인 경로를 통한 요청과 비정상적인 경로를 통한 요청을 서버가 구분하지 못할 경우, 공격자가 스크립트 구문을 이용하여 정상적인 사용자가 조작된(의도하지 않은) 요청을 전송하도록 하여 게시판 설정 변경, 회원 정보 변경 등의 문제를 유발하는 공격 기법. (또는) 특정 웹 사이트에 대해서 사용자가 인지하지 못한 상황에서 사용자의 의도와는 무관하게 공격자가 의도한 행위(수정, 삭제, 등록 등)을 요청하게 하는 공격 기법

**3) 소프트웨어(S/W) 개발 취약점을 보완하기 위한 방법**

1. 사용자 접근권한 정보가 포함된 임의의 토큰(CSRF 토큰)을 서비스 요청 전 단계에서 매번 새롭게 생성하여 발급하고, 요청 시 함께 전달하도록 한 후 요청에 포함된 토큰과 발급 시 해당 사용자 세션 정보에 저장한 토큰을 비교하여 정상적인 경로를 통한 요청인지 검증 (또는 입력화면 폼 작성 시 GET 방식보다는 POST 방식을 사용하고, 입력화면 폼과 해당 입력을 처리하는 프로그램 사이에 토큰을 사용하여 공격자의 직접적인 URL 사용이 동작하지 않도록 처리)
2. 중요한 기능에 대해서는 사용자 세션검증과 더불어 재인증을 유도
